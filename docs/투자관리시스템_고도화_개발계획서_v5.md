# 팀 투자 관리 시스템 고도화 개발 계획서 v5 (관리자 로그인 반영판)

> v4에서 이어지는 개정판입니다. "다음 확인이 필요한 사항" 4가지에 대한 답변을 반영합니다.
> **가장 큰 변화**: 1단계 인증을 "담당자 개별 로그인" 대신 **"관리자 단일 로그인(사이드바 하단 진입)"** 구조로 확정하고, 개별 담당자/SSO는 이 구조 위에 얹는 확장 슬롯으로 재배치합니다.

## ⚠️ 2026-07-24 갱신 — 편집/저장 방식 변경 (아래 1.3/2.1/2.2절 일부 대체)

이 문서의 1.2~1.4, 2.1, 2.2절에 설계된 **JWT + `edit_log.jsonl`(append-only 감사이력) + 별도 `/admin` 라우트** 구조는
2026-07-24 세션에서 사용자가 실제 구현을 진행하며 아래와 같이 더 단순한 방식으로 **대체 확정**했습니다.
이 문서의 나머지 내용(초기 아키텍처 논의 경과)은 히스토리로 남겨두고, 실제 구현 기준은 아래 표를 따릅니다.

| 항목 | 이 문서(v5)의 원안 | 실제 구현(2026-07-24 확정) |
|---|---|---|
| 진입점 | 사이드바 하단 "관리자 로그인" 텍스트 링크 → 로그인 모달 → 상세 테이블 행별 편집 아이콘 + 별도 `/admin` 라우트 | 사이드바 하단 **"관리자 설정"** 버튼 → 팝업(모달) 하나에서 로그인·편집·비밀번호 변경을 모두 처리. **별도 라우트/vue-router 없음** |
| 인증 토큰 | JWT, `users.json`에 bcrypt 해시 저장 | **opaque 토큰**(`secrets.token_urlsafe`), 서버 메모리에만 존재. 비밀번호도 파일 저장 없이 메모리 전용, 평문 상수시간 비교(`hmac.compare_digest`), **서버 재기동 시 항상 `admin`/`0000`으로 리셋** |
| 토큰 생존 | 명시 안 됨 | **메모리 전용** — 새로고침 시 로그아웃 (`sessionStorage` 사용 안 함) |
| 편집 이력 | `edit_log.jsonl`(append-only, 필드별 변경 전/후 값 기록) — 감사 이력 목적 | **폐기.** `data_rev/raw_2026_07_rev.dat`에 편집마다 **전체 데이터셋을 덮어쓰기** 저장. 누가/언제/무엇을 바꿨는지 이력은 남기지 않음(단일 관리자 프로토타입 단계라 불필요하다고 판단) |
| 서버 재기동 시 로드 | `base + edit_log.jsonl replay` | `data_rev/*_rev.dat`가 있으면 그것을 로드, 없으면 `base` 원본 로드 |
| 행 식별자 | `WBS_Code` | `WBS_Code`는 목업 데이터라 포맷 의미가 없어 **수기 입력 자유 필드**로 전환(빈 값/"예정" 등 허용, 중복 허용). 행의 실제 식별자는 **`NO`**(서버가 `max+1`로 자동 채번)로 변경 |
| 관리자 화면 구성 | `/admin`에 편집 이력 조회, 원본 파일 관리, 계정/SSO 설정 자리 | 팝업 내부 2탭: **(1) 전체 원본 데이터**(29개 컬럼 원본 그대로 + 행별 수정/추가 버튼 + CSV 다운로드) **(2) 비밀번호 변경** |
| 관련 코드 | — | `backend/app/data/edit_log.py`, `backend/data/current/`, `backend/data/edits/`는 **코드/파일은 남기되 호출부만 제거**(미사용 상태로 보존) |

실제 구현 상세(API 계약, 단계별 구현 순서, 신규/수정 파일 목록)는 세션 작업 시 작성한
플랜 문서(`관리자 로그인 + 데이터 편집 기능 설계`)를 참고하십시오.

## 1. 서브에이전트별 의견 (4차)

### 1.1 프로젝트 관리자(PM)

- 4번 답변으로 인증 범위가 명확해졌습니다. v2~v4에서 설계했던 "담당자 본인 소관 건만 편집"이라는 행(row) 단위 권한 모델은 **SSO 또는 개별 계정 체계가 갖춰졌을 때 켜는 확장 기능**으로 재배치하고, **1단계 실제 구현 대상은 "관리자 단일 계정 로그인 + 전체 파일 편집"**으로 확정합니다.
- 이렇게 되면 일반 사용자는 로그인 자체가 없는 "완전 조회 전용" 화면을 보고, 관리자만 사이드바 하단의 눈에 띄지 않는 진입점을 통해 로그인 후 편집 모드로 전환하는 흐름이 됩니다. **UI 복잡도가 낮아지고, 1단계 개발 범위도 축소되는 효과**가 있어 합리적인 방향이라 판단합니다.
- 다만 "전체 수정"이 가능한 단일 관리자 계정이므로, **누가 무엇을 고쳤는지에 대한 감사 이력(edit_log.jsonl)이 이전보다 더 중요**해집니다 — 담당자 구분이 없어 "관리자가 어떤 항목을, 언제, 어떻게 바꿨는지"가 유일한 추적 수단이기 때문입니다.

### 1.2 프론트엔드 개발자(FE)

**(a) 사이드바 UI 변경**
- 기존 사이드바 필터 목록(조직/계획구분/품의완료/팀장심의 의견/센터장 심의필요) 최하단에 구분선과 함께 작은 텍스트 링크 형태로 **"관리자 로그인"**을 배치 (평상시엔 존재감 없이, 필요한 사람만 인지하도록 눈에 띄지 않는 스타일)
- 클릭 시 **로그인 모달**(아이디/비밀번호 입력) 노출
- 로그인 성공 시:
  - 사이드바 해당 위치가 **"관리자 모드(로그아웃)"** 표시로 전환
  - 상세 테이블의 각 행에 **편집 아이콘**(연필)이 노출되고, 클릭 시 v2에서 설계한 `RowEditPanel.vue`(행 편집 패널)로 수정 가능
  - 별도 라우트 `/admin`으로 진입 가능한 **관리자 화면 메뉴**가 헤더 또는 사이드바에 추가로 노출

**(b) 관리자 화면(`/admin`) 구성안**
| 메뉴 | 내용 |
|---|---|
| 편집 이력 조회 | `edit_log.jsonl` 내용을 표 형태로 조회(누가/언제/어떤 항목/변경 전후 값) |
| 원본 파일 관리 | (선택) 신규 원본 파일 업로드 → 충돌 리포트 확인 → 반영 |
| 계정/권한 관리(자리만 확보) | 현재는 관리자 계정 1개뿐이므로 기능은 최소화하되, 화면 구조는 "향후 SSO 연동 시 사용자별 권한을 관리하는 화면"으로 확장될 수 있도록 레이아웃만 미리 잡아둠 |
| SSO 설정(자리만 확보, 비활성 표시) | 현재는 "추후 지원 예정" 안내만 표시되는 비활성 섹션으로 구성, 실제 SSO 연동 시 이 화면에서 활성화 |

**(c) 일반 사용자 화면**
- 로그인하지 않은 일반 사용자에게는 편집 아이콘, 관리자 메뉴 등 **일체의 편집 관련 UI를 노출하지 않음** — v2에서 고려했던 "담당자 여부에 따른 자물쇠/연필 아이콘 분기"는 이번 1단계에서는 보류(향후 개별 계정 도입 시 재활성화)

### 1.3 백엔드 개발자(BE)

**(a) 인증 API**
- `POST /api/v1/admin/login` — 아이디/비밀번호 검증 후 JWT 발급(역할: `admin`, 만료시간 설정)
- `users.json`에는 **관리자 계정 1~소수** 만 저장(v4에서 설계한 구조 그대로 사용, 다만 역할은 `admin` 고정)
- 비밀번호는 bcrypt 해시로 저장, 최초 비밀번호는 배포 시 관리자에게 별도 전달 후 최초 로그인 시 변경 강제

**(b) 편집 API 권한 검사 단순화**
- v2~v4에서 설계했던 "담당자 일치 여부 확인" 로직은 **코드 상에는 유지하되(향후 확장용), 1단계에서는 `role == admin`인 경우 전체 레코드에 대해 통과**하도록 권한 검사 우선순위를 조정
  ```
  권한검사(user, investment) =
      if user.role == "admin": 허용            # 1단계 실사용 경로
      elif investment.담당자 == user.표시명: 허용   # 코드는 유지, 개별 로그인 도입 전까지 미사용
      elif investment_permissions에 등록: 허용     # 코드는 유지, 위와 동일
      else: 거부
  ```
- 이렇게 하면 **향후 SSO/개별 계정이 추가돼도 API 로직을 다시 짤 필요 없이, 로그인 주체만 늘어나는 형태로 자연스럽게 확장**됩니다.

**(c) 감사 이력 강화**
- 관리자 단일 계정으로 전체 편집이 이뤄지는 구조이므로, `edit_log.jsonl`에 반드시 **수정 대상 항목의 식별자(WBS_Code), 변경 필드명, 변경 전/후 값, 수정 시각**을 빠짐없이 기록 (v4 설계 유지 + 필드 완결성 강조)
- 관리자 화면의 "편집 이력 조회" 메뉴가 바로 이 로그를 표로 보여주는 것으로 연결

**(d) 로그인 보안**
- 관리자 계정이 사실상 "만능 키"이므로, 로그인 시도 실패 횟수 제한(예: 5회 실패 시 일정 시간 잠금)을 애플리케이션 레벨에서 구현 제안

### 1.4 Nginx/K8s 운영 엔지니어(Infra)

**(a) Nginx 역할 확정**
- 1번 답변으로 **PDEP Ingress가 TLS 종료 및 외부 라우팅을 담당함이 확정**되었으므로, Nginx는 아래 역할만 담당하는 것으로 최종 확정합니다.
  - 프론트엔드 정적 파일(Vue 빌드 산출물) 서빙
  - `/api` 요청을 backend Service(K8s 내부 DNS, 예: `http://backend-svc:8000`)로 내부 프록시
  - TLS 인증서 관리, 외부 방화벽/네트워크 정책 설정은 **계획에서 제외**(Ingress/PDEP가 처리)

**(b) Jenkins 파이프라인 — 템플릿 규격 미확인 대응**
- 규격을 아직 모르므로, **범용적으로 통용되는 관례**에 맞춰 우리 쪽 산출물을 준비하고, 이후 실제 템플릿 확인 시 세부 조정만 하는 방식을 제안합니다.
  - 루트 경로에 표준 `Dockerfile` (멀티스테이지: FE 빌드 → Nginx 이미지 / BE 빌드 → Python 슬림 이미지)
  - `Jenkinsfile`은 `build → test → image push → deploy` 4단계의 범용 구조로 초안 작성
  - 이미지 태그 규칙: `{서비스명}:{커밋해시}` 기본 채택(템플릿이 다른 규칙을 요구하면 교체)
- **플랫폼팀에 확인할 체크리스트**를 별도로 준비(2.3절 참고) — 템플릿 규격 확인 즉시 반영 가능하도록

**(c) PVC/백업 — 정책 미확인 대응**
- StorageClass/백업 정책이 아직 없으므로, **애플리케이션 자체적으로 최소 안전장치를 1단계에 선반영**하는 것을 제안합니다.
  - K8s **CronJob**으로 매일 1회 `/data` 디렉터리를 타임스탬프가 붙은 압축 파일로 별도 경로(같은 PVC 내 `/data/_backup/`)에 백업
  - 플랫폼의 정식 StorageClass/백업 정책이 확인되면, 이 자체 백업은 "보조 수단"으로 유지하거나 플랫폼 백업으로 대체 여부를 재검토

**(d) 로그인 관련 보안 설정**
- `/api/v1/admin/login` 엔드포인트에 Nginx 레벨 **요청 속도 제한(rate limit)** 적용(무차별 대입 공격 대비, BE의 실패 횟수 제한과 이중 방어)

## 2. PM 최종 통합 계획

### 2.1 개정 아키텍처 (Ingress 확정 반영)

```
[사내망 사용자] ──▶ [PDEP Ingress (TLS 종료/라우팅, 플랫폼 제공)]
                              │
                 ┌────────────┴─────────────┐
                 ▼                          ▼
        ┌─────────────────┐        ┌──────────────────────┐
        │  Frontend Pod     │        │   Backend Pod          │
        │  Nginx(정적서빙+  │  /api  │   FastAPI               │
        │   내부 프록시)    │───────▶│  - 조회 API (인증 불필요) │
        └─────────────────┘        │  - /admin/login          │
                                     │  - 편집 API(admin 전용)  │
                                     └──────────┬──────────────┘
                                                │
                                        ┌───────┴────────┐
                                        │  PVC (/data)    │
                                        │  base/edits/    │
                                        │  current/       │
                                        │  users(admin)/  │
                                        │  _backup/(자체)  │
                                        └────────┬────────┘
                                                 │
                                        (K8s CronJob: 일일 자체 백업)
```

### 2.2 인증/권한 최종 확정

| 구분 | 1단계(이번 구현) | 확장 슬롯(구조는 유지, 미사용) |
|---|---|---|
| 조회 | 로그인 없이 전체 공개 | - |
| 편집 | **관리자 단일 계정 로그인 → 전체 레코드 편집** | 담당자 개별 로그인 → 본인 소관 건만 편집(SSO 또는 개별 계정 도입 시 활성화) |
| 진입 UI | 사이드바 필터 하단 "관리자 로그인" 링크 | 담당자별 개인 로그인 화면(추후) |
| 관리자 화면 | 편집 이력 조회, (선택)원본 파일 관리, 계정/SSO 설정 자리 확보 | 사용자별 권한 부여 화면(추후 실사용) |

### 2.3 Jenkins 템플릿 확인 체크리스트 (플랫폼팀 문의용)

1. Jenkinsfile 위치/이름 규칙이 정해져 있는지 (예: 루트의 `Jenkinsfile` 고정)
2. Docker 이미지 빌드 시 요구되는 필수 라벨/메타데이터가 있는지
3. 이미지 레지스트리 주소 및 push 인증 방식
4. Dev/Staging/Prod 환경별 배포 트리거 방식(브랜치 기준? 수동 승인?)
5. K8s 매니페스트를 Jenkins가 직접 apply하는지, 별도 GitOps(ArgoCD 등) 도구를 쓰는지

## 3. 이번 라운드에서 자체적으로 추가 제안한 사항

| # | 제안 | 근거 |
|---|---|---|
| 1 | 편집 API의 권한 검사 로직을 **"admin 우선 통과 + 기존 담당자 매칭 로직은 코드 상 유지"** 구조로 설계 | 지금은 관리자 전용으로 쓰지만, 나중에 SSO/개별 계정이 들어와도 API를 다시 짜지 않고 로그인 주체만 추가되도록 하기 위함(요청하신 "추후 SSO 관리" 대비) |
| 2 | 관리자 화면에 "SSO 설정(비활성 표시)" 섹션을 미리 배치 | 관리자 화면을 만들 때 지금 안 쓰는 기능이라도 자리를 미리 잡아두면, 추후 SSO 연동 시 UI를 다시 설계하지 않고 활성화만 하면 되도록 하기 위함 |
| 3 | 관리자 로그인 실패 횟수 제한 + Nginx 레이트리밋 이중 방어 | 단일 관리자 계정이 "만능 키" 역할을 하게 되므로, 일반적인 다중 사용자 시스템보다 더 엄격한 보안이 필요하다고 판단 |
| 4 | Jenkins 파이프라인을 "범용 관례 기반 초안"으로 먼저 준비하고 플랫폼팀 확인용 체크리스트를 별도로 분리 | 규격을 모른다고 작업을 못 하는 게 아니라, 일반적인 표준(Dockerfile, 4단계 파이프라인)으로 우선 준비해두면 실제 규격 확인 시 조정 폭을 최소화할 수 있음 |
| 5 | PVC 백업 정책 미확정 시 **애플리케이션 자체 CronJob 백업**을 임시 안전장치로 선반영 | 플랫폼 정책이 언제 확인될지 모르는 상태에서 무기한 리스크로 남겨두기보다, 우리 쪽에서 통제 가능한 최소한의 방어선을 먼저 만들어두는 것이 안전 |
