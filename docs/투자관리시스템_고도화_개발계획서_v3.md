# 팀 투자 관리 시스템 고도화 개발 계획서 v3 (사내 플랫폼 반영판)

> v2에서 이어지는 개정판입니다. 이번 개정 계기: **사내 개발 플랫폼 'PDEP'에 최종 배포/운영**하는 것을 전제로 계획을 보완합니다.

---

## 0. 조사 결과 안내 (먼저 확인 부탁드립니다)

PDEP에 대해 웹 검색을 진행했으나, **공개된 자료를 찾지 못했습니다.** 사내 전용 비공개 플랫폼으로 추정되어, 실제 기술 사양(런타임, CI/CD 방식, 인증 표준 등)은 외부 정보로는 확인이 불가능했습니다.

그래서 이번 v3는 두 부분으로 구성했습니다.
1. **일반적으로 대기업 사내 개발 플랫폼(PaaS형 내부 시스템)에 배포할 때 공통적으로 요구되는 항목**을 체크리스트로 정리 — 이는 PDEP의 실제 사양이 아니라, "확인이 필요한 항목"을 놓치지 않기 위한 일반 기준입니다.
2. 각 항목이 계획에 **어떻게 영향을 주는지**와, **현재 계획에 우선 반영한 가정(추후 확인 시 수정 필요)**을 명시했습니다.

> ⚠️ 아래 내용 중 "가정"이라고 표시된 부분은 확인이 필요한 사항입니다. 실제 PDEP 스펙을 알려주시면 해당 부분만 정확히 갱신하겠습니다.

---

## 1. 사내 플랫폼 배포 시 일반적으로 확인이 필요한 항목 체크리스트

| # | 항목 | 왜 계획에 영향을 주는지 | 이번 계획에 반영한 가정 (확인 필요) |
|---|---|---|---|
| 1 | **배포 런타임 형태** (Docker/Kubernetes 기반 PaaS vs VM 직접 설치) | v1~v2에서 제안한 "Docker Compose(nginx+FE+BE+DB+Redis)" 구성이 그대로 쓰일 수 있는지, 아니면 사내 컨테이너 이미지 규격(베이스 이미지, 이미지 스캔 정책)에 맞춰 재작성해야 하는지가 갈림 | **가정**: 사내 플랫폼이 컨테이너 기반 PaaS라고 가정하고 Docker 이미지 단위로 산출물을 준비하는 것으로 계획. PDEP 자체 오케스트레이션(K8s)을 쓴다면 Nginx 리버스프록시 역할 일부(TLS 종료, 라우팅)를 **플랫폼의 Ingress/API Gateway가 대신 담당**할 수 있어, Nginx 설정 범위가 축소될 수 있음 |
| 2 | **CI/CD 파이프라인 표준** (사내 Git, 사내 Jenkins/GitLab CI 등) | 빌드/배포 자동화 스크립트를 우리가 자체 설계할지, PDEP가 제공하는 파이프라인 템플릿에 맞춰 `Dockerfile`/빌드 스크립트만 제공하면 될지가 다름 | **가정**: 사내 Git 저장소 + 사내 CI 도구 존재를 전제로, 우리 쪽에서는 **표준 Dockerfile, 환경변수 목록, 헬스체크 엔드포인트(`/healthz`)**를 제공하는 것으로 계획에 반영 |
| 3 | **인증/SSO 연동** (사번 기반 사내 SSO) | v2에서 설계한 "자체 계정 + JWT" 방식이 사내 SSO로 대체될 가능성이 높음 — 이 경우 `users` 테이블은 SSO에서 내려주는 사번/부서 정보를 **동기화하는 캐시 테이블**로 역할이 바뀜 | **가정**: 사내 SSO 연동이 표준일 가능성이 높다고 보고, BE 인증 모듈을 **JWT 자체발급 방식과 사내 SSO 연동 방식 중 택일 가능한 구조(Strategy 패턴)**로 설계하도록 반영 |
| 4 | **네트워크 정책(망분리)** | 인트라넷 전용 서비스인지, 외부 접근이 필요한지에 따라 Nginx의 외부 노출 설정, HTTPS 인증서 발급 주체(사내 CA vs 공인 CA)가 달라짐 | **가정**: 사내망 전용(인트라넷)이라고 가정하고 계획. 이 경우 공인 인증서 발급 절차는 불필요할 수 있으며, 사내 CA 인증서 발급 절차를 Nginx 설정에 반영 필요 |
| 5 | **DB/스토리지 표준** (사내 지정 DB만 허용되는 경우가 많음) | v2에서 제안한 PostgreSQL이 사내 표준 DB와 다를 경우 교체 필요 | **가정**: 사내 표준 RDBMS 정책이 있을 수 있음을 감안해, ORM(SQLAlchemy)을 사용하도록 이미 설계 → **DB 종류가 바뀌어도 애플리케이션 로직 변경은 최소화**되도록 유지 (단, 방언 차이로 인한 마이그레이션 스크립트 일부 수정은 발생 가능) |
| 6 | **로깅/모니터링 표준** (사내 통합 로그 수집기 연동) | 자체 모니터링 스택(Prometheus/Grafana) 대신 사내 표준 로그 수집기로 로그 포맷/전송 방식을 맞춰야 할 수 있음 | **가정**: 애플리케이션 로그를 **표준 출력(stdout) 기반 JSON 로그**로 남기도록 설계 — 사내 로그 수집기가 stdout을 수집하는 방식이 일반적이므로 호환성 확보 |
| 7 | **보안 심사/코드 스캔 절차** (시큐어코딩, 취약점 점검, 오픈소스 라이선스 점검) | 개발 완료 후 배포 전에 사내 보안팀 심사가 있을 가능성이 높음 — 이 경우 일정에 **심사 기간**을 반영해야 함 | **가정**: 로드맵에 "보안 심사" 단계를 별도로 추가(5.2절 참고). 오픈소스 라이선스(예: ECharts-MIT, FastAPI-MIT 등)는 대부분 문제 없는 라이선스이나, 사내 정책상 화이트리스트 확인 필요 |
| 8 | **배포 승인/변경관리 절차** (ITSM 등 정식 변경관리 프로세스) | 배포가 곧바로 되는 게 아니라 변경 신청 → 승인 → 배포 창(윈도우) 절차를 거칠 수 있음 | **가정**: 로드맵 마지막 단계에 "배포 승인 리드타임"을 별도 버퍼로 반영 |
| 9 | **파일 업로드 정책** (`.dat`/Excel 업로드 시 사내 보안 정책상 파일 검사 필요 여부) | v1에서 제안한 업로드 API가 사내 정책상 바이러스 스캔/파일 확장자 제한 등을 거쳐야 할 수 있음 | **가정**: 업로드 API에 **확장자 화이트리스트 + 용량 제한**을 기본 반영하고, 사내 파일 검사 솔루션 연동 지점을 추후 확장 포인트로 남김 |
| 10 | **다중 환경 구성** (Dev/Staging/Prod, 사내 플랫폼이 환경별 배포를 강제하는 경우가 많음) | 환경별 설정 분리(DB 접속정보, API 도메인 등)가 필요 | **가정**: `.env` 기반 환경변수 분리 + 환경별 설정 파일(`config.dev.yaml`, `config.prod.yaml`) 구조를 기본 반영 |

## 2. 계획 반영 사항 정리 (v2 대비 변경/추가)

### 2.1 아키텍처 변경 — Nginx 역할 재정의

PDEP가 컨테이너 오케스트레이션(예: 사내 Kubernetes) 기반이라면, 아래처럼 **Nginx의 역할이 두 가지 시나리오로 나뉠 수 있습니다.**

| 시나리오 | Nginx 역할 |
|---|---|
| **A. PDEP가 Ingress/API Gateway를 자체 제공** | Nginx는 **컨테이너 내부에서 정적 파일 서빙 전용**으로 역할이 축소되고, TLS 종료/외부 라우팅은 플랫폼이 담당. 우리 쪽은 Nginx 설정을 단순화(정적 파일 서빙 + `/api` 내부 프록시만) |
| **B. PDEP가 VM 단위 배포만 지원 (직접 서버 구성)** | v1~v2에서 설계한 것처럼 Nginx가 **TLS 종료 + 리버스프록시 + 레이트리밋**을 모두 직접 수행 |

→ **계획에는 두 시나리오 모두 대응 가능하도록, Nginx 설정을 "정적 서빙용"과 "프록시/보안용"으로 분리한 2개의 설정 파일 세트로 준비**하는 것을 제안합니다. (Infra 에이전트 작업 항목에 추가)

### 2.2 인증 모듈 변경 — SSO 연동 가능 구조로 설계

v2에서는 "자체 계정 + JWT"만 고려했으나, 사내 플랫폼은 SSO 연동이 일반적이므로 BE 인증 모듈을 아래와 같이 **추상화 계층을 두어** 설계합니다.

```
AuthProvider (인터페이스)
 ├── LocalJWTAuthProvider   (자체 로그인, 초기 개발/테스트용)
 └── SSOAuthProvider        (사내 SSO 연동, 실제 운영 시 사용)
```

- `investments.담당자` 필드와 매칭할 식별자를 SSO가 제공하는 **사번**으로 통일 (문자열 이름 매칭보다 신뢰도 높음 — v2에서 지적한 "이름 매칭 실패" 리스크도 함께 해소)
- 개발 초기 단계(사내망 접속 전)에는 `LocalJWTAuthProvider`로 개발/테스트하고, PDEP 배포 시 `SSOAuthProvider`로 전환하는 2단계 방식 제안

### 2.3 로드맵 변경 — 사내 심사/승인 리드타임 반영

| 단계 | v2 내용 | v3 추가 사항 |
|---|---|---|
| 4. 통합/서빙 구성 | Docker Compose, Nginx 구성 | + **PDEP 배포 규격(Dockerfile, 헬스체크, 환경변수 목록) 문서화** |
| 5. 고도화 | 알림, 엑셀 export | (변경 없음) |
| 6. QA/배포 | 실데이터 검증, 성능 테스트 | + **사내 보안 심사 신청 및 대응(1~2주 버퍼)**, **변경관리(ITSM) 승인 절차(리드타임 확인 필요)** |

### 2.4 데이터 모델 변경 — 사번 기반 사용자 식별로 통일

- `users.employee_id`(사번)를 기본 식별자로 승격, `투자명(변경전)`/`담당자(변경전)`처럼 원본 데이터에 있던 "이름 기반 텍스트"는 **표시용으로만 유지**하고 권한 판단은 사번 매칭으로 전환
- 이렇게 하면 v2에서 언급한 "이름 매칭 실패(동명이인/오탈자)" 리스크가 실질적으로 해소됨

## 3. 이번 라운드에서 자체적으로 추가 제안한 사항

| # | 제안 | 근거 |
|---|---|---|
| 1 | Nginx 설정을 "정적 서빙용"과 "프록시/보안용" 2세트로 미리 분리 설계 | PDEP가 자체 Ingress를 제공하는지 여부에 따라 Nginx 역할이 크게 달라질 수 있어, 어느 쪽이든 대응 가능하게 하기 위함 |
| 2 | 인증 모듈을 `AuthProvider` 추상화로 설계 (Local vs SSO) | 사내 SSO 존재 여부를 아직 모르는 상태에서 개발을 시작해야 하므로, 나중에 SSO 확정 시 재설계 없이 구현체만 교체 가능하게 하기 위함 |
| 3 | 사용자 식별자를 이름 대신 **사번** 기준으로 전환 | v2에서 지적했던 "이름 매칭 실패" 리스크를 사내 SSO 연동 시 근본적으로 해소할 수 있는 기회로 판단 |
| 4 | 로드맵에 **보안 심사/변경관리 리드타임**을 별도 버퍼로 명시 | 사내 대기업 시스템은 실제 배포 전 심사 절차가 일정에 큰 영향을 주는 경우가 많아, 이를 누락하면 일정 산정이 부정확해짐 |
| 5 | 파일 업로드 API에 확장자/용량 제한을 기본값으로 선반영 | 사내 파일 검사 정책 확정 전이라도 최소한의 보안 기본기는 갖춰두는 것이 안전 |

## 4. 다음 확인 요청 (다시 한 번 정리)

계획을 더 정확히 다듬기 위해, 아래 중 아시는 내용만이라도 알려주시면 바로 반영하겠습니다.

1. PDEP가 **컨테이너(Docker/K8s) 기반**인지, **VM 직접 배포** 방식인지
2. **사내 SSO** 연동이 필수/권장인지 여부
3. **망분리(인트라넷 전용)** 여부 및 외부 접근 필요성
4. 사내에서 **표준으로 지정된 DB**가 있는지 (있다면 종류)
5. 배포 전 **보안 심사/변경관리 절차**가 있는지, 대략적인 소요 기간

정보가 확인되는 대로 해당 항목만 골라서 계획을 갱신하겠습니다. 확인이 어려운 항목은 위 표의 "가정"을 유지한 채로 진행해도 무방합니다 (추후 구현 단계에서 유연하게 대응 가능하도록 이미 설계했습니다).
