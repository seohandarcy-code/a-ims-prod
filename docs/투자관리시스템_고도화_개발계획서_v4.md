# 팀 투자 관리 시스템 고도화 개발 계획서 v4 (No-DB / K8s 반영판)

> v3에서 이어지는 개정판입니다. 이번 개정은 PDEP 사양에 대한 답변 5가지를 반영합니다.
> **가장 큰 변화는 "DB 없는 파일 기반 시스템" 결정**으로, 데이터 계층 설계 전체가 바뀝니다.

---

## 0. 답변 반영 요약

| # | 질문 | 답변 | 영향 범위 |
|---|---|---|---|
| 1 | 배포 형태 | **Docker/Kubernetes(사내 PaaS)** | 아키텍처, Nginx 역할, 무상태(stateless) 설계 필요성 |
| 2 | CI/CD | **사내 GitHub + Jenkins** | 파이프라인 설계, Dockerfile, 이미지 태깅 전략 |
| 3 | SSO | **필수 아님, 단 추후 연동 가능하도록 선택형(pluggable) 구조 유지** | 인증 모듈 설계 확정 |
| 4 | 망분리 | **사내망 환경, PDEP가 네트워크 연결을 대신 처리** | Nginx/네트워크 보안 설정 범위 축소 |
| 5 | DB | **DB 없이, 백엔드가 원본 데이터를 로드 + 수정정보 관리 + 최신 파일을 생성/유지하는 파일 기반 구조** | **데이터 계층 전면 재설계** (가장 큰 변경) |

## 1. 서브에이전트별 의견 (3차)

### 1.1 프로젝트 관리자(PM)

- **"DB 없는 시스템"은 운영 부담을 줄이는 합리적 선택**이라고 판단합니다. 다만 이 결정에는 트레이드오프가 따르므로, PM으로서 아래 2가지를 이번 계획에서 명확히 짚고 넘어가야 한다고 봅니다.
  1. **다중 인스턴스(수평 확장) 제약**: 파일을 직접 읽고 쓰는 구조는 파드(Pod)가 2개 이상 뜨면 동시 쓰기 충돌이 발생할 수 있습니다. → **1단계는 단일 인스턴스(Replica=1)로 운영**하는 것을 전제로 계획을 확정합니다. (팀 단위 내부 시스템 규모이므로 트래픽상 무리 없음)
  2. **PVC(영구 볼륨) 필수화**: K8s 파드는 재시작 시 컨테이너 내부 파일이 초기화되므로, 데이터가 보존되려면 **PersistentVolumeClaim이 반드시 필요**합니다. 이는 Infra 에이전트 작업에 필수 항목으로 추가합니다.
- SSO는 "선택형 구조"로 이미 v3에서 설계 방향(`AuthProvider` 추상화)을 잡아뒀으므로 그대로 유지하되, **기본값(SSO 미사용) 상태에서의 로컬 계정 운영 방식**을 이번에 구체화해야 함을 BE에 요청합니다.

### 1.2 프론트엔드 개발자(FE)

- 이번 답변은 FE 화면/시각화 설계 자체에는 큰 영향이 없습니다. (v2에서 정리한 디자인 토큰, 컴포넌트 명세, 라이트/다크 테마 계획은 그대로 유지)
- 다만 배포 방식이 K8s로 확정되면서, **빌드 산출물(정적 파일)이 Jenkins 파이프라인에서 Docker 이미지로 패키징**되는 흐름이 됩니다. 따라서 FE 빌드 시 아래 사항을 계획에 반영합니다.
  - 프로덕션 빌드 시 API 주소를 하드코딩하지 않고 **런타임 환경변수 주입 방식**(예: 빌드 후 `config.js`를 컨테이너 시작 시 치환)으로 설계 — 환경(Dev/Staging/Prod)별로 이미지를 다시 빌드하지 않아도 되도록
  - SSO 연동 여부에 따라 로그인 화면이 "자체 로그인 폼" 또는 "SSO 리다이렉트" 두 가지로 분기될 수 있으므로, 로그인 페이지를 **모드 분기 가능한 컴포넌트**로 미리 설계

### 1.3 백엔드 개발자(BE) — 파일 기반 데이터 계층 설계 (핵심)

DB 없이 운영하기 위해, 아래와 같은 **"원본 + 변경분 오버레이 + 병합 결과"** 3단 구조를 제안합니다.

**(a) 파일 구조안**

```
/data
 ├─ base/
 │   └─ raw_2026_07.dat            # 원본 데이터 (읽기 전용, 팀에서 전달받은 그대로 보관)
 ├─ edits/
 │   └─ edit_log.jsonl             # 편집 이력 append-only 로그 (한 줄 = 편집 1건)
 ├─ permissions/
 │   └─ investment_permissions.json # 관리자가 부여한 예외 편집 권한
 ├─ users/
 │   └─ users.json                  # 로컬 계정 (SSO 미사용 시), 비밀번호는 해시로 저장
 └─ current/
     └─ current_dataset.dat         # base + edits를 병합한 "최신 파일" (매 편집 시 재생성)
```

**(b) 동작 방식**
1. 서버 기동 시 `base/raw_*.dat`를 pandas로 로드 → 메모리에 적재
2. `edit_log.jsonl`을 처음부터 순서대로 재생(replay)하여 메모리 상의 데이터에 변경분을 반영
3. 조회 API는 **메모리 상의 병합 결과**로 응답 (파일을 매번 읽지 않아 성능 확보)
4. 편집 API 호출 시:
   - 권한 검사(담당자 일치 또는 `investment_permissions` 확인)
   - `edit_log.jsonl`에 변경 내역 append (원자적 쓰기: 임시파일 작성 후 rename)
   - 메모리 상의 데이터 갱신
   - `current/current_dataset.dat` 재생성 (요청하신 "최신 파일 유지" 요구사항 충족)
5. 신규 원본 파일(`base/raw_2026_08.dat` 등)이 들어오면, WBS_Code 기준으로 기존 편집 이력과 재매칭하여 병합 — 충돌(원본 값이 이미 바뀐 경우) 시 관리자에게 "충돌 리포트"로 안내

**(c) 동시성/무결성 설계**
- 편집 API는 **단일 비동기 락(asyncio.Lock)** 으로 직렬화 — 파일 하나에 여러 요청이 동시에 쓰지 않도록 보장
- 앞서 PM이 지적한 대로, **파드는 반드시 1개(Replica=1)** 로 운영 (다중 파드 확장 시엔 별도의 조율 장치—예: 리더 선출—가 필요하므로 이번 단계 범위에서 제외)
- `edit_log.jsonl`이 감사 이력 역할을 겸함 (v2에서 설계한 `investment_history`를 파일 기반으로 대체)

**(d) 인증 저장소**
- SSO 미사용 시: `users.json`에 계정(아이디, 비밀번호 해시, 표시 이름, 매칭할 담당자명) 저장, 관리자가 계정 생성 시 특정 `담당자` 값과 1:1로 연결
- SSO 사용 시: `users.json`은 "최근 로그인한 사번 캐시" 역할로 축소, 실제 인증은 SSO 토큰 검증으로 위임
- `AUTH_MODE=local|sso` 환경변수로 전환 (v3에서 설계한 `AuthProvider` 추상화 그대로 적용)

**(e) 캐시**
- DB가 없으므로 Redis 없이도 무리가 없다고 판단 — **메모리 상의 병합 결과 자체가 캐시 역할**을 겸함. 1단계에서는 Redis를 계획에서 제외하여 인프라 구성을 단순화 (필요 시 추후 확장)

**(f) 확장성 한계 명시**
- 이 구조는 데이터 규모가 수백~수천 행 수준의 팀 단위 시스템에 적합합니다. 향후 데이터가 크게 늘거나(예: 여러 팀 통합) 다중 인스턴스 확장이 필요해지면, **SQLite(임베디드, 서버 불필요) → PostgreSQL** 순서로 전환하는 것을 검토 대상으로 남겨둡니다. (지금 당장 도입하자는 것은 아니며, 향후 옵션으로만 기록)

### 1.4 Nginx/K8s 운영 엔지니어(Infra)

- PDEP가 망분리·네트워크 연결을 대신 처리해주므로, **TLS 종료/네트워크 보안 설정 상당 부분을 플랫폼에 위임**할 수 있습니다. 이에 따라 Nginx의 역할을 아래처럼 단순화합니다.
  - Nginx는 **프론트엔드 파드 내부에서 정적 파일 서빙 + `/api` 요청을 백엔드 서비스로 내부 프록시**하는 역할만 담당
  - 외부 라우팅/TLS는 PDEP의 Ingress(또는 플랫폼 게이트웨이)가 담당한다고 가정 (확인 필요 항목으로 남김)
- **PVC(PersistentVolumeClaim) 신규 필수 항목**: `/data` 디렉터리를 담을 영구 볼륨을 K8s 매니페스트에 반드시 포함해야 함 — 이게 없으면 파드 재시작 시 모든 편집 이력이 소실됨 (No-DB 구조의 가장 큰 운영 리스크)
- **백업 전략 필요**: DB는 보통 자체 백업/복제 기능이 있지만, 파일 기반은 그렇지 않으므로 `/data` 볼륨을 **주기적으로 스냅샷/외부 백업**하는 절차를 PDEP 운영팀과 협의해야 함
- **Jenkins 파이프라인 설계(초안)**:
  1. 사내 GitHub push/PR 트리거
  2. FE 빌드(Vue) → 정적 산출물 생성
  3. BE 빌드 → FastAPI 앱 Docker 이미지 빌드 (FE 정적 산출물을 Nginx 이미지에 포함하거나 별도 이미지로 분리)
  4. 이미지 사내 레지스트리에 push (태그: 커밋 해시 + 브랜치)
  5. K8s 매니페스트(Deployment/Service/PVC/ConfigMap/Secret) apply — Dev/Staging/Prod 환경 분기
  6. 헬스체크(`/healthz`) 통과 확인 후 배포 완료 처리
- **K8s 매니페스트 구성 요소(초안)**: `Deployment`(frontend, backend 각 1 replica), `Service`(내부 통신용), `PVC`(backend `/data`), `ConfigMap`(비민감 설정), `Secret`(로컬 계정 비밀번호 해시 salt, JWT 시크릿 등)

## 2. PM 최종 통합 계획

### 2.1 개정 아키텍처 (K8s / No-DB 반영)

```
[사내망 사용자]
     │  (PDEP가 망분리/연결 처리)
     ▼
┌─────────────────────────────────────────────┐
│         PDEP Ingress / Gateway (플랫폼 제공)    │  ← TLS 종료, 외부 라우팅 (확인 필요)
└───────────────┬─────────────────────────────┘
                │
     ┌──────────┴───────────┐
     ▼                      ▼
┌─────────────┐     ┌───────────────────┐
│ Frontend Pod │     │   Backend Pod       │
│  Nginx        │────▶│  FastAPI(Uvicorn)   │
│  (정적서빙+   │ /api │  - 조회/편집 API     │
│   내부 프록시)│     │  - AuthProvider      │
└─────────────┘     │   (local|sso 전환)   │
                     └─────────┬───────────┘
                               │
                        ┌──────┴───────┐
                        │  PVC (/data)  │
                        │  base/edits/  │
                        │  current/     │
                        │  users/perms  │
                        └───────────────┘
```
- Replica: Frontend는 여러 개 가능(무상태), **Backend는 1개로 고정** (파일 동시 쓰기 문제 방지)
- Redis/PostgreSQL 미사용 (1단계 기준)

### 2.2 인증 설계 확정

```
AuthProvider (인터페이스)
 ├── LocalFileAuthProvider   # AUTH_MODE=local (기본값) — users.json 기반, bcrypt 해시
 └── SSOAuthProvider         # AUTH_MODE=sso   — 추후 연동 시 활성화
```
- 환경변수 `AUTH_MODE`로 전환, 코드 재설계 없이 운영 중 전환 가능하도록 설계
- 로컬 모드에서는 관리자가 `users.json`에 계정 생성 시 **투자 데이터의 `담당자` 값과 1:1 매핑**을 직접 지정 (자동 매칭 불가하므로 수동 지정 UI를 관리자 화면에 포함)

### 2.3 로드맵 갱신

| 단계 | 내용 | v3 대비 변경 |
|---|---|---|
| 1. 설계 | ERD → **파일 스키마 설계**(edit_log 포맷, current_dataset 포맷)로 대체, OpenAPI, 디자인 토큰 | DB 설계 대신 파일 포맷 설계 |
| 2. BE 개발 | 파일 기반 로드/병합/재생 로직, 편집 API, AuthProvider(local 우선 구현) | 데이터 계층 로직 전면 신규 |
| 3. FE 개발 | (v2와 동일) + 런타임 환경변수 주입 방식 반영 | 소폭 변경 |
| 4. 통합/배포 | Jenkinsfile, Dockerfile, **K8s 매니페스트(Deployment/Service/PVC/ConfigMap/Secret)** | 신규 인프라 산출물 다수 추가 |
| 5. 고도화 | 알림, 엑셀 export, (신규) `/data` 백업 자동화, SSO 연동(필요 시) | 백업 자동화 추가 |
| 6. QA/배포 | 보안 심사, 변경관리 승인, **단일 인스턴스 운영 부하 테스트**, **파드 재시작 시 데이터 보존 검증(PVC 테스트)** | 파일 기반 특유의 검증 항목 추가 |

### 2.4 리스크 테이블 갱신 (No-DB 관련 신규 항목)

| 리스크 | 대응 |
|---|---|
| 파드 재시작/재스케줄 시 데이터 소실 | PVC 필수 적용 + 배포 전 "파드 삭제 후 재생성 → 데이터 보존" 시나리오 테스트를 QA 단계에 명시적으로 포함 |
| 다중 인스턴스 확장 불가 | 1단계는 Replica=1로 명시, 향후 트래픽 증가 시 SQLite/PostgreSQL 전환을 확장 옵션으로 미리 문서화 |
| `edit_log.jsonl` 무한 증가 | 주기적(예: 분기별) 스냅샷 압축 정책 수립 — 과거 로그를 아카이브 파일로 이동하고 `current_dataset`은 항상 최신 상태 유지 |
| 파일 손상(비정상 종료 중 쓰기 실패) | 모든 쓰기는 "임시파일 작성 → rename" 원자적 방식 적용, 손상 감지 시 직전 백업본으로 자동 복구하는 로직 포함 |
| 로컬 계정 비밀번호 관리 부담(SSO 미사용) | 비밀번호는 bcrypt 해시로만 저장, 최초 비밀번호는 관리자가 발급 후 최초 로그인 시 강제 변경 |
| 원본 파일 교체 시 편집 이력과의 충돌 | WBS_Code 기준 재매칭 + 충돌 리포트 화면 제공 (자동 덮어쓰기 금지) |

## 3. 이번 라운드에서 자체적으로 추가 제안한 사항

| # | 제안 | 근거 |
|---|---|---|
| 1 | **Backend Replica=1 고정** 원칙을 명시적으로 계획에 못박음 | 사용자가 "DB 없음"을 요청했을 때 암묵적으로 따라오는 제약(동시 쓰기 문제)을 명확히 하지 않으면 추후 K8s 운영 중 다중 파드로 스케일링을 시도하다 데이터 정합성 사고가 날 수 있음 |
| 2 | **PVC 필수화**를 인프라 작업 항목에 최우선으로 추가 | No-DB 구조에서 파일이 곧 유일한 데이터 저장소이므로, 이를 놓치면 파드 재시작만으로 전체 데이터가 사라지는 심각한 사고로 이어짐 |
| 3 | `edit_log.jsonl` append-only 로그를 **v2의 `investment_history` 테이블을 대체하는 감사 이력**으로 명시적으로 연결 | DB가 없어졌다고 감사 이력 요구사항까지 사라지는 것은 아니므로, 파일 기반으로도 동일한 목적을 달성하도록 설계를 이어감 |
| 4 | 원본 파일 교체 시 **충돌 리포트** 메커니즘 제안 | 매달 원본 데이터가 갱신될 가능성이 높은데, 그사이 발생한 수정 이력과 새 원본이 충돌할 수 있는 시나리오는 사용자가 언급하지 않았지만 반드시 짚어야 할 부분이라 판단 |
| 5 | Redis를 1단계 계획에서 제외 | DB를 없애기로 한 취지(운영 단순화)에 맞춰, 굳이 필요하지 않은 별도 캐시 서버까지 없애는 것이 일관된 방향이라 판단 |
| 6 | SQLite/PostgreSQL 전환을 "향후 확장 옵션"으로만 기록 (지금 도입 안 함) | 사용자의 명확한 지시("일단 DB 없는 시스템")를 존중하되, 나중에 규모가 커졌을 때의 이관 경로를 미리 남겨 의사결정 부담을 줄이기 위함 |

## 4. 다음 확인이 필요한 사항

1. PDEP의 Ingress/Gateway가 **TLS 종료 및 외부 라우팅을 실제로 대신 처리**하는지 (Nginx 역할 범위 확정에 필요)
2. 사내 레지스트리 주소 및 Jenkins 파이프라인 템플릿 존재 여부 (있다면 그 규격에 맞춰 Jenkinsfile 초안 작성 가능)
3. PVC용 **StorageClass**(사내 PaaS가 제공하는 스토리지 종류)와 **백업/스냅샷 정책**을 PDEP 운영팀에 문의 필요
4. 로컬 계정(1단계 인증) 운영을 **관리자 1인이 전담**할지, 별도 관리자 화면이 필요한 규모인지 확인

이 항목들은 몰라도 계획대로 진행 가능하며, 확인되는 대로 해당 부분만 갱신하겠습니다. 계획에 이견 없으시면 다음은 ERD 대신 **파일 스키마/편집 로그 포맷 상세 설계** 또는 **코드 스캐폴딩** 중 원하시는 방향으로 진행하겠습니다.
