# 팀 투자 관리 시스템 고도화 개발 계획서 v2 (개정판)

> v1: `투자관리시스템_고도화_개발계획서.md`에서 이어지는 개정판입니다.
> 이번 개정의 계기: **(1)** 시각화 디자인 레퍼런스 이미지 3종 검토, **(2)** "조회 기반 + 담당자 본인 항목 수정" 기능 범위 확정 요청
> 이번 단계도 **계획 수립 단계**이며, 코드 구현은 계획 확정 후 별도로 진행합니다.

## 1. 시각화 레퍼런스 이미지 분석

### 이미지 1 — 라이트 테마 실무용 대시보드
| 구성 요소 | 관찰된 디자인 특징 | 의미 |
|---|---|---|
| 상단 KPI 카드 6개 | 흰 배경, 옅은 테두리, 라운드 코너, 라벨(작게)+값(크게) 2단 구성 | v1의 `kpi-card` 구조와 동일 — 그대로 계승 가능 |
| **단계 전환율 카드** (품의대상→품의완료, 품의완료→계약등록, 계약등록→집행발생) | 카드마다 큰 퍼센트 숫자 + `25/34건` 형태의 분수 라벨 + 색상이 입혀진 굵은 가로 진행바. 3개 카드가 **품의(블루) → 계약(퍼플) → 집행(그린)** 순서로 색이 바뀜 | v1에는 없던 **"단계 전환 퍼널(funnel)" 시각화**. 원본 로직(신호등, 집행률)에 있는 단계 개념을 시각적으로 요약하는 새로운 위젯 → **신규 컴포넌트로 채택** |
| **조직별 인라인 리스트바** (조직별 품의완료 건수 등) | 조직명 좌측 텍스트, 우측에 진행바가 있고 **진행바 채워진 부분 안에 "완료 9건" 뱃지 텍스트가 겹쳐서 표시**, 맨 우측에 전체 건수(`12건`) | 막대 안에 라벨을 병기해 별도 범례 없이 값을 바로 읽게 하는 방식 → **신규 컴포넌트로 채택** |
| **콤보 차트(월별 누적 금액/건수)** | 옅은 회색 막대(월별 값) + 진한 색 라인(누적값) + 라인 끝점에 "최종 120.7" 콜아웃 라벨 | v1에서 Plotly로 이미 유사 차트가 있었음 — ECharts 이식 시 **끝점 콜아웃 라벨**을 필수 스펙으로 명시 |
| 섹션별 색상 코드 | 품의=블루(`#1428A0` 계열), 계약=퍼플, 집행=그린으로 섹션 전체가 통일 | **단계별 색상 토큰 확장**이 필요 (v1 THEME에는 퍼플/그린 계열 부재) |

### 이미지 2, 3 — 다크 프레젠테이션 테마
| 관찰 | 의미 |

## 2. 서브에이전트별 2차 의견

### 2.1 프로젝트 관리자(PM)

- 이번 요구사항은 "**조회 시스템 + 제한된 자기 소관 편집**"으로, v1에서 리스크로 지목했던 "범위 미확정" 문제를 해결하는 결정입니다. **승인 워크플로우는 이번 범위에서 명시적으로 제외**하되, 데이터 모델과 API는 나중에 승인 단계를 끼워 넣어도 재설계가 필요 없도록 설계해야 함을 BE/FE에 공통 지침으로 전달합니다.
- 편집 권한의 1단계 규칙을 다음과 같이 명확히 정의합니다.
  - **기본값**: 모든 사용자는 조회만 가능
  - **예외**: 로그인한 사용자의 사번/계정이 특정 투자 건의 `담당자` 필드와 일치하면 해당 건에 한해 지정된 필드만 수정 가능
  - **확장점**: 시스템 관리자가 특정 사용자에게 특정 건(또는 조직 단위)에 대한 편집 권한을 "부여"하면, 담당자가 아니어도 편집 가능해지는 구조 (관리자 화면은 이번 단계 범위에 포함, 단 승인 프로세스 자체는 미포함)
- 디자인 시스템 구축은 "코드 작업"이 아니라 **계획 단계에서 산출물(디자인 토큰 표, 컴포넌트 명세, 목업)까지 정리**하고, 실제 구현은 이후 코딩 단계에서 진행하는 것으로 정리합니다.

### 2.2 프론트엔드 개발자(FE) — 시각화 구현 방법론 + 편집 UX

**(c) 편집 기능 UX 설계 방향**
- 상세 테이블에서 로그인한 사용자가 담당자인 행에는 **연필 아이콘**을, 아닌 행에는 **자물쇠 아이콘**을 표시해 권한 여부를 직관적으로 구분
- 편집은 "인라인 셀 편집"이 아니라 **행 단위 편집 패널(사이드시트/모달)**로 진행 — 여러 필드를 한 번에 수정하고 "저장 전 변경사항 확인" 단계를 넣어 오입력 방지
- 저장 시 서버가 반환하는 **변경 이력**(누가/언제/무엇을 바꿨는지)을 편집 패널 하단에 바로 노출 — 담당자 스스로도 이력을 확인 가능하게 함
- "내 담당 건만 보기" 필터를 사이드바에 추가 제안(v1 필터 목록에 없던 항목)

### 2.3 백엔드 개발자(BE) — 인증/권한/편집 API

- **인증**: 이번 단계는 사내 시스템 규모를 고려해 **자체 계정 + JWT 기반 로그인**을 최소 구현으로 제안(추후 사내 SSO 연동 여지는 남겨둠). `users` 테이블에 `사번` 또는 `계정ID`를 두고, `investments.담당자` 문자열과 매칭되는 사용자 계정을 자동 연결(최초 로그인 시 매칭, 매칭 실패 건은 관리자가 수동 연결)
- **권한 모델**: 단순 Role(뷰어/편집자/관리자)만으로는 "담당자 본인 건만 편집"이라는 요구를 표현할 수 없으므로, **행(건) 단위 권한 테이블**을 별도로 둡니다.
  - `investment_permissions (investment_id, user_id, granted_by, granted_at)` — 관리자가 이 테이블에 명시적으로 행을 추가하면 편집 가능
  - 기본 규칙: `투자건.담당자 == 로그인사용자.표시명` 이면 **암묵적으로 편집 가능** (별도 grant 없이도 가능, "본인 소관 건" 요구사항 충족)
  - 확장 규칙: 관리자가 `investment_permissions`에 특정 사용자를 추가하면 담당자가 아니어도 편집 가능 (이번 단계에 관리자 화면 포함)
- **편집 API**: 전체 필드가 아니라 **편집 허용 필드 화이트리스트**를 서버에서 강제(예: 팀장심의_의견, 계약_월 등은 담당자가 고칠 수 있지만, `NO`, `WBS_Code` 같은 식별 필드는 고정)
  - `PATCH /api/v1/investments/{id}` — 요청 시 서버가 `담당자 일치 여부` 또는 `investment_permissions` 존재 여부를 확인 후 처리, 불일치 시 403
  - 저장 시 `investment_history`에 변경 전/후 스냅샷 자동 기록 (v1에서 제안한 이력 테이블 재사용)
  - **동시 편집 충돌 방지**: `updated_at` 기반 낙관적 잠금(Optimistic Lock) — 편집 시점과 저장 시점의 `updated_at`이 다르면 충돌로 처리하고 최신값을 보여준 뒤 재확인 요청
- **승인 워크플로우로의 확장 여지 확보**: 이번 단계에서는 만들지 않지만, `investment_history`에 이미 `변경 전/후` 스냅샷이 쌓이므로 향후 "승인 대기" 상태를 추가할 때 `investment_history.status`(예: `applied`/`pending_approval`) 컬럼만 추가하면 재설계 없이 확장 가능 — 이 점을 스키마 설계 시 미리 감안

### 2.4 Nginx 운영 엔지니어(Infra)

- 편집(쓰기) 기능이 생기므로 **로그인 세션/토큰이 오가는 구간은 반드시 HTTPS**로 강제(HTTP 요청은 308 리다이렉트)
- 쓰기 API(`PATCH`, `POST`)에는 조회 API보다 낮은 **레이트리밋**을 별도로 설정해 오남용/실수로 인한 대량 수정 방지
- JWT를 쿠키로 운용할 경우 `HttpOnly`, `Secure`, `SameSite=Strict` 속성 강제, CORS는 프론트엔드 도메인만 허용하도록 명시적 화이트리스트 구성
- 프레젠테이션 모드(`/present`)는 자동 새로고침이 들어갈 수 있어 **정적 캐시 우회 헤더**(`Cache-Control: no-store`)를 해당 경로에 별도 적용 검토
- 편집 API 접근 로그는 감사 목적상 access log 보존 기간을 조회 API보다 길게 설정하는 것을 제안

## 3. PM 최종 통합 수정 계획

### 3.1 범위 재정의 (3단계 로드맵으로 명확화)

| 단계 | 범위 | 이번 개발 대상 여부 |
|---|---|---|
| **1단계 (이번 범위)** | 조회 대시보드 전체 + 담당자 본인 소관 건 편집(화이트리스트 필드) + 관리자의 편집 권한 수동 부여 기능 + 변경 이력 기록 | **✅ 포함** |
| 2단계 (향후) | 편집 시 "제출 → 팀장/센터장 승인" 상태 흐름(워크플로우 엔진), 승인 알림 | 이번 범위 **제외**, 스키마 확장으로 대응 가능하도록 설계만 반영 |
| 3단계 (향후) | 신규 투자 건 자체를 시스템에서 기안/생성, 결재선 연동 | 이번 범위 **제외** |

### 3.4 디자인 시스템 구축 프로세스 (계획 단계 산출물 정의)

이번 계획 단계에서 아래 산출물을 먼저 확정하고, 실제 코드 구현은 그 다음 단계로 넘깁니다.

1. **토큰 표 확정본** (2.2절 표 기준, 색상/폰트/여백 수치까지 확정)
2. **컴포넌트 명세서** (2.2절 표를 props/데이터 스키마 수준까지 구체화한 별도 문서)
3. **화면별 와이어프레임**(조회 탭 2종 + 프레젠테이션 모드 + 편집 패널) — 목업 이미지 또는 텍스트 명세로 정리
4. **더미 데이터 기반 컴포넌트 검증 계획**(Storybook 도입 여부 결정)

> 이 산출물들은 원하시면 이어서 별도 문서/목업으로 작성해 드릴 수 있습니다.
