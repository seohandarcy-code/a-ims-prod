## 1. 현재 상태(Before)와 문제점

현재 `DiagnosisTable.vue`는 `max-height:300px` 스크롤 표에 7개 컬럼(NO / 조직 / 담당자 / 투자명 / 진단단계 / 진단내용 / 관리포인트)을 한 줄씩 나열한다.

문제점:
1. **진단단계 배지가 단색 한 종류.** stage(품의 지연/계약 대기/집행 대기/잔여 집행)와 무관하게 전부 `--blue-step-1` 배경 + `--samsung-blue` 글자 한 색이다. 단계 흐름(품의→계약→집행)이 배지에서 전혀 읽히지 않아, 레퍼런스 이미지 1의 단계색 언어(품의=블루 / 계약=퍼플 / 집행=그린)와 어긋난다.
2. **정보 밀도가 낮은데도 한눈에 안 들어온다.** 진단내용/관리포인트가 긴 문장이라 표에서는 셀이 여러 줄로 줄바꿈되어 행 높이가 들쭉날쭉하고, 300px 안에 2~3건만 보인다. "지금 뭘 먼저 처리해야 하나"라는 우선순위 판단에는 오히려 방해가 된다.
3. **순위(우선순위) 개념이 시각적으로 없다.** 백엔드가 stage로부터 매핑한 `priority`(품의지연=1 … 잔여집행=4)와 정렬 순서가 있는데도, 화면에는 순위 감각이 전혀 노출되지 않는다(dead field).

## 2. 개선 방향(After 공통 원칙)

- **요약/상세 분리:** 카드 헤더에는 순위·NO·조직·담당자·투자명·진단단계 배지만. 긴 문장인 진단내용/관리포인트는 펼쳤을 때만 노출 → 스캔용 밀도 확보(5개 남짓 보이고 넘치면 스크롤).
- **단계색 배지:** soft 배경 + 진한 글자. 품의 지연→블루(#1428A0/#DBEAFE), 계약 대기→퍼플(#7C3AED/#EDE9FE), 집행 대기·잔여 집행→그린(#059669/#D1FAE5). 레퍼런스 이미지 1의 3단계 색 언어를 그대로 계승.
- **중립 팔레트 통일:** 텍스트/보더는 2026-07-21 확정 중립(neutral) 토큰(#171717/#525252/#A3A3A3/#E5E5E5)으로. 기존 `--blue-step-*` 계열 대신 단계색은 stageColors 리터럴을 사용.
- **순위 노출:** dead field였던 순위를 카드에 노출. 단, `priority`(단계 버킷 값)는 카드마다 중복되므로 **정렬 순서 인덱스(1~N)를 시각적 랭킹**으로 쓰고, `priority`(단계 버킷)는 배지/보조 칩으로 표기하는 것을 권장.

## 4. 추천

- **1순위 추천: 안 A(리스트형 아코디언)를 기본 컴포넌트로.** 두 화면 모두 커버 가능하고 가장 콤팩트하며, 단계색 배지만으로도 Before의 핵심 문제(단색 배지·낮은 스캔성)를 해결한다.
- **보완: 대시보드 top10에는 안 C의 "큰 랭킹 넘버 + 단계 레일"을 옵션(prop)으로 얹는 것을 권장.** 종합현황은 "무엇을 먼저 처리하나"를 강조하는 화면이므로 랭킹 강조가 유효하다.
- **상세 top12(감사 성격)에는 안 B의 명시적 [상세] 버튼 방식이 더 안전.** 한 건씩 근거를 열어 확인하는 흐름에서 오조작이 적고 어포던스가 분명하다.
- 즉, **단일 컴포넌트 + variant prop(`rank`/`toggle` 표시 방식)** 로 A를 코어로 두고 C/B의 요소를 화면별로 켜는 구조를 제안한다.

### frontend-dev 구현 참고(지시)
- 대상 파일: `frontend/src/components/table/DiagnosisTable.vue` (또는 `PriorityCardList.vue`로 신규 분리 후 두 View에서 교체).
- 배지 색: 하드코딩 금지. `theme/stageColors.ts`의 stage→color/soft 매핑을 사용해 `stage` 문자열로 클래스/스타일을 결정("품의 지연"→po, "계약 대기"→contract, "집행 대기"·"잔여 집행"→execution).
- 순위: `priority` 필드를 직접 랭킹 숫자로 쓰지 말 것(버킷값이라 중복). `v-for` 인덱스+1을 랭킹으로 사용하고, `priority`는 필요 시 보조 칩(버킷명)으로만 노출.
- 요약/상세: 헤더=순위/NO/조직/담당자/투자명/배지, 상세(펼침)=`detail`(진단내용)/`action`(관리포인트). 펼침 상태는 각 행 로컬 state(`ref`/`Set`)로 관리.
- 컨테이너: `max-height`로 5개 남짓 노출 + `overflow-y:auto` 유지(기존 300px 표 대체). 카드 radius 1rem, shadow `0 1px 2px rgba(15,23,42,0.06)`.
- 접근성: 안 A/C의 카드 클릭 토글에는 `role="button"`+`aria-expanded`+키보드(enter/space) 처리 추가 권장. 안 B는 실제 `<button>` 사용이라 시맨틱 확보됨.

## 구현 관점 (PM/frontend-dev 종합)

frontend-dev가 실제 코드(`DiagnosisTable.vue` / `DashboardView.vue` / `StatusDetailView.vue` / `types/api.ts` / `theme/*`)를 읽고 정리한 조사 결과를 종합한다. 이번 라운드에서 `frontend/src`는 한 줄도 수정하지 않았다.

### 확인된 코드 사실
- `DiagnosisTable.vue`는 `rows` 하나만 받는 순수 프레젠테이셔널 컴포넌트(정렬/필터 없음, `max-height:300px` 스크롤 표). 두 화면이 공유한다.
- **폭:** 대시보드의 "관리 우선순위"는 `org-col(200px 고정) + body-col(flex:1)` 안의 `.two-col { 1fr 1.6fr }` 오른쪽 칼럼 → 실사용 폭은 전체의 약 62%(1920px에서도 대략 500~600px). 상세현황은 org-col이 없어 더 넓다.
- **반응형 관례가 사실상 없음:** `theme/tokens.css`에 `@media`가 전무하고, 프로젝트 전체에서 `@media`를 쓰는 파일은 `SidebarFilters.vue` 하나뿐인 데스크톱 전용 대시보드.
- **접근성 선례:** `SidebarFilters.vue`가 이미 `button + :aria-expanded + aria-controls` 패턴을 씀(네이티브 `<details>` 아님). 이게 코드베이스의 기존 관례.
- **stage 색 매핑 공백:** `stageColors.ts`의 `STAGE_NAME_MAP`은 "품의완료/계약등록/집행발생"(완료형)만 매핑. 진단단계 4종 "품의 지연/계약 대기/집행 대기/잔여 집행"(병목형)은 미매핑이라 현재는 중립색으로 폴백.
- **백엔드 비대칭:** `make_priority_action_table`(대시보드용)만 `priority`(1~4 stage 버킷값)를 세팅. `make_bottleneck_table`(상세현황용)은 `priority` 없이 동일 스키마로 반환. 정렬은 `(priority, no)`.

### frontend-dev 권고 요약
1. **컴포넌트 분리:** `DiagnosisTable.vue`는 그대로 두고(공유 컴포넌트라 내부를 카드로 바꾸면 상세현황 표 요구와 충돌), 신규 `PriorityCard.vue`(개별 카드) + 리스트 컨테이너를 추가. `props: rows`만 같고 표현이 다른 두 컴포넌트를 병존시키는 게 안전.
2. **펼침 상태:** 카드별 로컬 `ref<boolean>` 권장. 여러 건을 동시에 펼쳐 비교하는 게 자연스러워, 부모 `expandedId`로 강제 아코디언(하나 열면 이전 닫힘)은 이점 없음.
3. **접근성:** 기존 관례대로 `<button type="button" :aria-expanded :aria-controls>`로 카드 헤더 전체를 감싸기(아이콘만 버튼이면 타깃 과소). button은 Enter/Space가 네이티브 동작이라 별도 keydown 불필요. 펼칠 때 포커스 강제 이동은 지양(리스트 순차 탐색 흐름 유지). 카드=`<li>`, 리스트=`<ul>`로 감싸 스크린리더에 "N개 중 M번째" 맥락 제공.
4. **백엔드:** 대시보드 카드형은 현재 응답으로 변경 불필요(`DiagnosisRow` 필드로 요약/상세 분리 충분). priority 비대칭은 "상세는 표 유지" 결론을 따르면 무해. **지금 backend-dev 협의 불필요** — 다만 훗날 상세현황도 카드화하기로 하면 그때 `make_bottleneck_table`에도 동일 `priority_map` 적용을 요청한다는 메모만 남김. (DB 도입/스키마 대변경 아님 — 기존 계산 필드 노출 수준.)
5. **반응형:** 신규 `@media` 추가보다 `grid-template-columns: repeat(auto-fill, minmax(240px, 1fr))` 같은 콘텐츠 기반 반응형이 무-브레이크포인트 관례와 부합. 좁은 대시보드 칼럼에서는 1열, 넓은 화면에선 자동 2열. 컨테이너는 기존처럼 `max-height + overflow-y:auto`로 높이 급증 방지.
6. **stage→색 매핑 위치:** `STAGE_NAME_MAP`에 섞지 말고 `stageColors.ts`에 진단단계 전용 맵(`DIAGNOSIS_STAGE_MAP`)+함수(`diagnosisStageColorByName`)를 별도 추가. 완료형("완료/등록/발생")과 병목형("지연/대기")은 의미가 반대라 한 맵에 섞으면 오독 위험. 색 팔레트(`STAGE.*`)는 재사용. "집행 대기" vs "잔여 집행"을 같은 그린으로 둘지 톤 구분할지는 디자인 판단.

### 디자이너 안 vs frontend-dev 안의 상충 지점 (오너 판단 필요)
- **핵심 상충:** ui-designer는 "A를 코어로 한 **단일 컴포넌트 + variant prop**으로 두 화면 모두 카드화"를 제안. frontend-dev는 "**대시보드만 카드(PriorityCard 신규), 상세현황(top12·감사용)은 표 유지**, `DiagnosisTable.vue`는 존치"를 권장. → 두 화면을 모두 카드로 통일할지, 대시보드만 카드로 갈지가 1차 결정 사항.
- **공통분모(이견 없음):** (a) 배지 색은 하드코딩 금지·`stageColors` 매핑 사용, (b) 랭킹은 `priority`가 아니라 `v-for` 인덱스+1, (c) `DiagnosisTable.vue`를 삭제하진 않음.

### 오너 결정 체크리스트

### 제약 준수 확인
- No-DB / 백엔드 Replica=1 / 인증 범위 / PVC / Nginx 역할 등 계획서 확정 사항과 무관한 순수 프론트 표현 계층 변경이다. 백엔드는 기존 계산 필드(`priority`) 노출 수준까지만 논의됐고 스키마 대변경·DB 도입은 없다. plan_v5 변경 사유 없음.
