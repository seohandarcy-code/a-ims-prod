## Round 2 — 기능별 검토 (병렬)

### frontend-dev 응답 요약

| 의제 | 판단 | 공수 | 영향 파일 수 |
|---|---|---|---|
| 1 | 토큰(`tokens.css`)+상수모듈(`stageColors.ts`) **의도적 이중 정의** 방식 타당(ECharts는 CSS 변수 못 읽음). `StageFlowChart.vue`만 시리즈 단일색→data item별 color로 구조 변경 필요, 나머지는 리터럴 치환 | 하~중 | 6~7 |

| 3 | 좁은 채움(예 14%) 라벨 폴백은 **순수 CSS 불가** — 텍스트가 부모보다 넓은지 감지하는 표준 CSS 방법이 없음. **고정 임계값(22~25% 미만이면 라벨을 트랙 밖으로)** 방식을 1단계로 권장. `ResizeObserver` 실측은 정확하지만 FOUC 방지 등 공수 증가 | 중 | 2 |
| 4 | `emphasizeLast` prop 가능하나, "누적집행률" 라인처럼 배열 끝이 아니라 중간에서 `null`로 끊기는 케이스가 있어 **"마지막 non-null 인덱스"** 계산 필요 | 중 | 4~5 |
| 5 | 기능 영향 없는 순수 스타일 변경 | 하 | 2 |
| 6 | **vue-router 도입 권장**(계획서 명시 스펙, `window.location.pathname` 임시방편보다 정합적). EChar트 스무딩라인/시작점마커/최소축라벨 재현 난이도 낮음~중간. 가장 큰 공수는 차트가 아니라 **신규 다크 컴포넌트 세트 + 격리된 라우트/부트스트랩** — 위젯 1~2종으로 좁혀도 1~2일 규모 | 상 | 8+ |

### backend-dev 응답 요약 (실제 코드 확인 기반: `status_detail.py`, `dashboard.py`, `stage.py`, `org.py`, `monthly.py`, `store.py`)

| 의제 | 판단 |
|---|---|
| 2 | `overview_kpi`는 "사이드바 필터→조직버튼 필터" 순으로 스코프가 정확히 반영됨(변경 불필요). `execution_conversion_rate`가 100%를 넘는 건 계약등록 없이 집행이 잡히는 케이스가 있어서이며 **legacy 계산식을 그대로 이식한 의도된 동작**(신규 버그 아님) — 프론트가 값을 은폐하면 안 됨 |
| 3 | `groupby` 특성상 0건 조직은 배열에 아예 나타나지 않음(total=0 행 생성 불가), 호출부도 `total_df=None` 고정이라 더 확실함 — **변경 불필요**, 프론트 방어코드는 권장 수준 |
| 4 | `monthly_flow`는 애초에 기준월까지만 생성돼 문제 없음. `po`/`contract`/`execution`의 `monthly_table` 3개는 1~12월 전체가 내려오되 "누적" 필드만 기준월 이후 `null` — 필드명도 제각각이라 null 유무만으로 판단하면 실수하기 쉬움. **`/api/v1/meta`의 `current_month`와 배열 인덱스 대조를 1차 기준으로 삼을 것**을 권장(코드 변경 아닌 프론트 가이드 필요 사항) |
| 6 | 기존 `execution_monitoring` 응답 재사용으로 충분, 별도 경량 엔드포인트 불필요(현재 데이터 규모에서 폴링 성능 문제 없음, 메모리 상 재계산 방식이라 캐시 미스도 없음) |

### infra-devops 응답 요약 (실제 파일 확인 기반: `nginx/nginx.conf`, `vite.config.ts`, `package.json`, `tokens.css`)

- **사실관계**: Dockerfile·K8s 매니페스트 전무. 현재 `nginx.conf`는 정적 서빙이 아니라 순수 dev 리버스프록시(전부 Vite dev서버로 `proxy_pass`)라 **prod용 nginx 설정 자체가 아직 없음**. `vue-router`도 `package.json`에 없음. `tokens.css`의 `font-family: Pretendard`는 실물 폰트 파일/`@font-face` 없이 시스템 폴백 상태.
- **딥링크 새로고침**: dev 환경은 Vite dev server 기본 SPA 폴백에 "우연히" 얹혀갈 뿐 검증 안 됨. prod는 아직 설정이 없어 전혀 커버 안 됨 — 향후 prod `nginx.conf`에 `try_files $uri $uri/ /index.html;` 필수.
- **`/present` 캐시 정책**: `location = /present { add_header Cache-Control "no-store" always; ... }`를 `location /`보다 우선순위 높게 별도 추가 필요(`add_header` 비상속 특성 주의). 해시 붙은 정적 asset은 반대로 장기캐시 유지.
- **폰트 셀프호스팅**: Dockerfile이 없어 멀티스테이지 빌드 자체를 처음 설계해야 함. 확인 필요 항목으로 보류(실사용 weight/서브셋 여부, Jenkins 폐쇄망 npm 미러, 라이선스 재배포 가능 여부, PDEP 이미지 용량 제한).

## Round 3 — pm-coordinator 종합

### 충돌·의존성

- **(A) 의제6만 구조적 결정이다.** 의제1~5는 기존 SPA 위 컴포넌트/토큰 수준(저위험, 롤백 쉬움). 의제6만 `vue-router` 도입 + 격리 라우트가 걸린 되돌리기 비용 있는 결정.
- **(B) 의제6은 FE만의 문제가 아니다.** `/present`의 SPA 폴백·캐시 정책은 **prod nginx.conf 신규 작성**을 유발하는데, Dockerfile·K8s·prod nginx.conf가 전부 없는 현재 상태에서는 "완결"이 불가능 — FE만 먼저 하고 prod 서빙은 로드맵 4단계로 이월하는 분할이 필요.
- **(C) 의제4는 이미 유보 항목 + 숨은 공수 추가 발견.** "사용자 확인 후"로 이미 유보됐는데, Round 2에서 4개 엔드포인트의 배열 길이·null 규칙이 서로 달라 **일관 처리가 생각보다 까다롭다**는 게 추가로 드러남.
- **(D) 값 은폐 금지 제약 확정 필요.** `execution_conversion_rate` 100%+ 는 정확한 값이므로 "바는 클램프하되 분수라벨엔 실제값"을 구현 제약으로 못박아야 함(옵션 아님).

### 실행 순서 옵션

| 옵션 | 내용 | 장점 | 단점 | PM 판단 |
|---|---|---|---|---|
| **A** | 저위험 묶음(1→2→3→5) 먼저, 의제6은 별도 라운드 | 전부 SPA 내부 변경, 인프라 무변경, 롤백 쉬움. plan_v5 3단계 범위에 정확히 안착 | 다크 프레젠테이션(계획서 명시 스펙)이 뒤로 밀림 | 권장 |
| **B** | router부터 도입해 그 위에 1~5를 얹음 | 구조를 한번에 정리, 다크 스펙 조기 확보 | 저위험 항목까지 6의 리스크에 인질로 잡힘. prod nginx가 없어 어차피 배포 레벨 검증은 못 함 — "구조 먼저"의 이점이 절반만 실현 | 비권장 |
| **C(절충)** | 1·2·3·5 먼저 완료 + 의제6은 **FE 골격만** 병렬 착수, prod 서빙(nginx/Dockerfile)은 로드맵 4단계로 명시 이월 | 저위험 가치를 빨리 실현하면서 다크 스펙도 죽이지 않음 | 의제6이 "dev는 되는데 prod 미검증" 상태로 걸쳐 있음 — 완료 정의를 명확히 해야 함 | A와 함께 권장 |

### 범위·로드맵 정합성 코멘트

- 의제1~6 전부 **plan_v5 로드맵과 충돌 없음**(3단계 FE 범위 안, 다크 테마도 계획서 명시 스펙) — 순수하게 순서/타이밍 선택 문제.
- Dockerfile/K8s 부재가 의제6에 주는 영향은 큼: FE는 지금 가능하지만 배포 레벨 완결(딥링크·캐시)은 4단계 산출물이 나와야 검증 가능. 의제6 착수 시 "완료 정의"를 FE 한정으로 할지 prod까지 포함할지 반드시 명시해야 함(포함 시 로드맵 4단계 일부 조기 실행이 되며, 이 경우에도 Backend Replica=1·PVC 필수·Nginx 역할 한정 등 기존 제약은 그대로 유지).
- router 선행 도입이 1~5에 주는 실익은 거의 없음(1~5는 라우팅 비의존) → 6을 뒤로 미루는 비용은 낮음.

## 사용자 결정 필요 항목 (체크리스트)

1. **실행 순서**: A(저위험 먼저·6 별도 라운드) / B(router 먼저, 비권장) / C(1·2·3·5 먼저 + 6 FE골격 병렬, prod서빙 4단계 이월) — **PM 권고: A 또는 C**
2. **의제4 포함 여부**: (a) 이번 제외(권고) / (b) 저위험 묶음에 포함 / (c) 의제6과 함께 별도 트랙
3. **의제6 착수 여부·완료 정의**: (a) 이번엔 착수 안 함 / (b) 착수하되 FE+dev 한정(prod는 4단계 이월) / (c) 착수 + prod nginx.conf/Dockerfile까지 포함(4단계 일부 조기 실행 승인)
4. **의제6 범위**: 착수 시 위젯 1~2종으로 좁힐지, 풀 컴포넌트 세트로 갈지
5. **의제3 구현 방식**: 고정 임계값(권고, 공수 중) vs `ResizeObserver` 실측(정확하지만 공수 큼)
6. **확인성 항목(승인만 필요)**:
   - 의제2·3 "100%+ 값 은폐 금지 — 바는 클램프, 분수라벨은 실제값" 구현 제약 확정 (권고: 확정)
   - 의제4 포함 시 `/api/v1/meta.current_month` 기준 인덱스 대조를 라벨 판정 기준으로 문서화 (권고: 확정)
   - 폰트 셀프호스팅은 이번 라운드 보류, 4단계 전에 infra-devops의 확인 필요 항목(weight/서브셋, 폐쇄망 npm 미러, 라이선스, 이미지 용량) 회수 (권고: 보류 유지)

**PM 요약 권고**: 옵션 A 또는 C + 의제4 이번 제외 + 의제6 착수 시 FE 한정 완료정의(prod서빙 4단계 이월) + 의제3 임계값 방식 — 이 조합이 리스크·로드맵 정합성 기준으로 가장 균형 잡혀 있다. 최종 선택은 사용자 몫이다.
