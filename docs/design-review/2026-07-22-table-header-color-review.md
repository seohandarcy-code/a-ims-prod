## 1. 오너 요청
표 헤더를 현재 "옅은 회색 배경(#F5F5F5) + 검정 글씨"에서 **"검정 배경 + 흰 글씨"**로 변경. 목적은 중립색 검정 계열(`--text-main`/`--neutral-strong` = #171717)과의 통일감 강화.

## 2. 확인된 현황 (팩트)
- 5개 표 전부 `.simple-table th`: `background: var(--neutral-soft)`(#F5F5F5) + color 미지정 → `--text-main`(#171717) 상속 + th 기본 bold. 즉 이미 "옅은 회색 + 굵은 검정 글씨".
- 전역 토큰은 `frontend/src/theme/tokens.css`의 `:root`에 정의(`--neutral-soft` L32, `--text-main` L21, `--neutral-strong` L31). `style.css`는 `tokens.css` import 한 줄뿐.
- **핵심 발견(양 에이전트 공통)**: `--neutral-strong`(#171717, 채워진 검정)은 이미 **"선택/활성" 어포던스 전용**으로 쓰인다 — `OrgButtonFilter.vue`(선택 버튼 배경 검정+흰 글씨), `SidebarFilters.vue`의 `.active` 패턴. 즉 화면에서 "채워진 검정 면"은 이미 "지금 선택된 것"이라는 의미를 가진다.
- sticky 헤더 3곳 배경은 알파 없는 순수 hex → 검정으로 바꿔도 불투명 유지, 스크롤 시 아래 행 비침 없음.
- th 내부에는 배지/progress/정렬아이콘/링크 등 색 상속 자식이 전무(순수 텍스트). 배지·progress는 전부 `td` 전용.
- 다크/프레젠테이션 테마(`/present`)는 아직 미구현. 현재 `data-theme="dark"`가 적용되는 지점이 없어 이번 변경과 충돌 없음.
- docs/ 하위에 UI 레퍼런스 이미지는 **존재하지 않음**(검색 0건). 톤앤매너 판단은 토큰 체계 + 실제 컴포넌트 기준.

## 3. 디자이너 의견 (ui-designer)
결론: **완전 검정 채움 헤더에 반대.** 1순위 대안 권고.
- (1) 상세현황 화면은 SimpleRecordTable 다수 + StageDetailTable + DiagnosisTable이 세로로 쌓여, 검정 밴드가 4~6개 반복 → "black stripe" 효과로 부드러운 흰 패널 미학과 충돌, 데이터보다 헤더가 무거워짐.
- (2) 흰 카드 위 검정 밴드 = 페이지 최강 대비(black-on-white). 의미상 낮은 컬럼 헤더가 KPI/제목/선택 버튼보다 시각적으로 세지는 **위계 역전**. "채워진 검정 = 선택됨" 신호와 충돌해 검정의 의미가 희석됨. → 통일감이 아니라 오히려 표만 튐.
- (3) 본문 단계색(블루/퍼플/그린)은 중명도라 바로 위 명도 0 검정에 눌려 의미 신호가 죽음(특히 이미 약한 progress-fill).
- 대안 평가: (a) 진회색 #262626/#404040 — 개선폭 작음. (b) 배경 유지·텍스트만 강조 — 가장 가볍지만 체감 변화 거의 없고 오너 요구 미충족. **(c) 헤더 하단 굵은(2px) 검정 밑줄 + 불투명 라이트 배경 유지 + 굵은 근검정 텍스트 — 검정을 '면'이 아니라 '선'으로 반영해 오너 요구 충족하면서 무겁지 않고 위계·단계색 보존.** (d) 하이브리드 — DetailTable 헤더만 채운 다크, 나머지는 밑줄형.
- **1순위: (c).** 오너가 "채워진 질감"을 고수하면 차선으로 (c)+(d) 결합.
- 별개 관찰: `DiagnosisTable`의 `.stage-badge`가 단계 무관 하드코딩 블루 → 단계색 언어 매핑은 별도 이슈.

## 4. 프론트 의견 (frontend-dev)
결론: **오너 요청(검정+흰 글씨)은 구현상 안전·저리스크.** 디자인 채택 여부와 무관하게 기술 리스크 없음.
- (a) 통합 vs 개별: 전역 클래스 승격은 과잉 추상화로 판단. `tokens.css`에 이미 있는 `--neutral-strong` 재사용이 최소 변경. 다만 5곳 복붙 값이 나중에 벌어지지 않도록 **`--table-header-bg` / `--table-header-text` 의미 토큰을 `tokens.css`에 신설**하고 5개 파일이 그 토큰만 참조하게 하는 정도를 권장(전역 클래스 승격은 아님).
- (b) sticky 3곳: #171717은 불투명 solid → 문제 없음.
- (c) 배지/progress는 전부 td 전용, th엔 없음 → 색 충돌 없음.
- (d) th 내부 색 상속 자식 없음 → `color:#fff` 부작용 없음.
- (e) 다크 테마 미적용 → 현재 충돌 없음. 단 향후 프레젠테이션 다크 카드가 어두워지면 검정 th가 카드 배경과 동화될 수 있어, (a)의 헤더 전용 토큰 도입이 그 리스크까지 커버.
- 부수: th `border-bottom`(#E5E5E5 연회색)이 검정 배경 위에선 거의 안 보임 → 필요시 조정(필수 아님).

## 5. 의견 정렬/차이 요약
- **차이(디자인 방향)**: 디자이너는 "완전 검정 채움 반대, 밑줄형(c) 권고". 프론트는 디자인 방향에 관여하지 않고 "검정+흰 글씨든 뭐든 구현은 안전"이라는 입장 → **정면충돌 아님.** 디자이너는 미학·위계 근거로 다른 안을 제시했고, 프론트는 어느 안이든 실현 가능함을 확인.
- **공통 발견**: 두 에이전트 모두 독립적으로 "채워진 검정 = 선택/활성"이 이미 확립된 신호임을 지적 → 헤더까지 채운 검정으로 만들면 이 의미가 희석된다는 점은 양측 근거가 일치.
- **공통 권고(구현 위생)**: 5곳 복붙 대신 `--table-header-bg`/`--table-header-text` 의미 토큰 도입(전역 클래스 승격은 불필요). 어떤 최종안을 택하든 이 토큰화는 유효.

## 6. PM 종합 권고
**부분 채택 / 톤 조정안을 1순위로 오너에게 제안.**
- 오너의 명시적 요청은 "검정+흰 글씨"이며, 이는 plan_v5 등 확정 계획을 벗어나지 않는 순수 시각 결정(로컬 화면 완성 단계 범위 내)이라 최종 선택권은 오너에게 있다.
- 다만 디자이너 근거(위계 역전 + "채워진 검정=선택됨" 의미 충돌 + 검정 밴드 반복)가 구체적이고, 프론트도 그 의미 충돌을 독립 확인했으므로, **PM 권고는 디자이너 (c)안(굵은 검정 밑줄 + 라이트 배경 유지 + 굵은 텍스트)을 1순위로 제시**한다.
- 오너가 "채워진 검정 질감"을 반드시 원하면 **(c)+(d) 하이브리드**(hero 표 DetailTable만 채운 검정, 반복되는 SimpleRecordTable 등은 밑줄형)를 차선으로 권고.
- 어느 안이든 구현 시 **헤더 전용 의미 토큰(`--table-header-bg`/`--table-header-text`)을 `tokens.css`에 도입**하고 5개 파일이 참조하게 해, 향후 톤 재조정·다크 테마 대응을 한 곳에서 하도록 한다.
