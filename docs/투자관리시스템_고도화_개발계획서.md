# 팀 투자 관리 시스템 고도화 개발 계획서

> 대상 원본: `web_new5_transfer_minus_detail.py` (Streamlit, 약 3,744줄) + `raw_new.dat` (29개 컬럼, 34행 샘플)
> 목표 스택: **Vue(FE) + FastAPI(BE) + Nginx(서빙/리버스프록시)**
> 참여 서브에이전트: 프로젝트 관리자(PM) / 프론트엔드 개발자(FE) / 백엔드 개발자(BE) / Nginx 운영 엔지니어(Infra)

---

## 0. 공통 분석: 원본 시스템 요약

4명의 에이전트가 공통으로 확인한 원본 시스템의 특징은 다음과 같습니다.

| 구분 | 내용 |
|---|---|
| 데이터 소스 | `raw_new.dat` (탭 구분, UTF-8-SIG, 29개 컬럼) — 인코딩/구분자 자동감지 로직 존재 |
| 도메인 | IT 투자 예산관리: **계획 → 팀장/센터장 심의 → 기본품의 → 계약등록 → 기성(집행)** 단계별 진행 관리 |
| 핵심 필드 | 조직, 담당자, WBS_Code, 투자명, 계획구분(계획/계획외/Drop), 팀장심의예정/의견, 센터장심의, 투자비(계획/실행/증액/전용), 기본품의금액, 기성단계·월·금액(다건은 `/`로 구분), 기성 예측치 |
| 화면 구성 | 탭1 "투자 종합현황"(KPI 6종 + 조직별/월별 차트), 탭2 "투자 진행 상세현황"(품의/계약/집행 3개 서브탭 + 건별 진단 테이블 + 월별 비교) |
| 설계상 장점 | `COL`, `THEME`, `APP_CONFIG`, `KPI_CARDS`, `SIDEBAR_FILTERS`, `DETAIL_TABLE_COLUMNS`, `STATUS_CHARTS` 등 **설정(config)-드리븐** 구조 → 컬럼/색상/필터가 바뀌어도 로직 수정 최소화 |
| 구조적 한계 | 단일 파일·단일 프로세스, 정적 파일 직접 읽기(동시 편집/이력 관리 불가), 인증/권한 없음, 캐시가 프로세스 메모리(`st.cache_data`)에 종속, 데이터 검증/입력 UI 부재(파일을 수작업으로 교체하는 구조로 추정) |

이 분석을 4개 에이전트가 각자의 관점에서 더 파고들었습니다.

## 1. 프로젝트 관리자(PM) 에이전트 — 1차 의견

**역할**: 전체 요구사항 종합, 우선순위/일정/리스크 관리, 에이전트 간 인터페이스(API 계약, 데이터 스키마) 조율

### 분석
- 원본이 이미 "설정값과 로직의 분리"를 잘 해뒀다는 점을 **자산**으로 판단. FE/BE 분리 시 `COL`(컬럼 매핑), `THEME`(디자인 토큰), `KPI_CARDS`/`STATUS_CHARTS`(위젯 정의)를 **백엔드가 내려주는 메타데이터(config API)**로 승격하면, 컬럼이 바뀌어도 프론트 재배포 없이 대응 가능.
- 원본은 "조회 전용 대시보드"이지만, 실제 팀 운영에서는 담당자가 매달 `.dat`를 교체하는 것으로 보임 → 이를 **정식 데이터 입수/등록 기능**으로 승격할지 여부가 프로젝트 범위의 핵심 의사결정 포인트.
- 심의예정월 경과(🟡 신호등), 집행 지연 등은 이미 로직이 있으나 "알려주는" 기능(알림)은 없음 → 고도화 포인트로 채택.

### 초기 계획 골격 제안
1. **Phase 0** 요구사항 확정 (범위: 조회전용 대시보드 vs 데이터 입력/승인 워크플로우 포함 여부)
2. **Phase 1** 데이터 계층 설계 + API 계약(OpenAPI) 확정
3. **Phase 2** BE 핵심 API 구현, FE 뼈대/디자인시스템 구현 (병행)
4. **Phase 3** 통합, Nginx 서빙/배포 파이프라인
5. **Phase 4** 고도화 기능(알림, 이력, 엑셀 export, 권한) + QA

## 2. 프론트엔드 개발자(FE) 에이전트 — 의견

**역할**: Vue 기반 화면/차트/상태관리/디자인시스템 전담

### 분석
- 원본 Streamlit 화면은 사실상 **KPI 카드 그리드 + Plotly 차트 + 데이터 테이블**의 반복 조합이며, `THEME` 딕셔너리가 이미 디자인 토큰(색상/여백/폰트 크기) 형태로 정리되어 있어 **CSS Variables 혹은 Design Token 파일로 그대로 이식 가능**.
- `st.tabs`(대탭 2개, 소탭 3개) 구조는 Vue Router의 nested route 혹은 tab 컴포넌트로 1:1 매핑 가능.
- Plotly 차트(막대/파이/라인, 조직별 정렬 적용된 가로 막대 등)는 **ECharts**(Apache) 또는 **Vue-ChartJS**로 대체 권장 — ECharts가 원본의 스택형 막대/이중축 라인/파이 조합을 가장 근접하게 재현 가능.
- 상세 테이블(`DETAIL_TABLE_COLUMNS`, `집행률` progress bar, 검색, 20행+스크롤)은 Vue 컴포넌트로 **가상 스크롤 지원 테이블**(예: TanStack Table for Vue, 또는 자체 구현)이 필요 — 34행짜리 샘플이지만 실제 운영 데이터는 수백 건 이상일 가능성 고려.

### 제안 사항
- **기술 스택**: Vue 3 (Composition API + `<script setup>`) + TypeScript + Pinia(상태관리) + Vue Router + ECharts + Element Plus 또는 naive-ui(데이터 테이블/폼 컴포넌트 활용도 높음)
- **디자인 토큰화**: 원본 `THEME`를 `design-tokens.ts` + CSS 변수로 이식, 삼성 블루(`#1428A0`) 등 색상 체계 유지
- **컴포넌트 분해안**:
  - `KpiCardGrid.vue`, `KpiCard.vue`
  - `OrgFilterBar.vue`, `FilterSidebar.vue`
  - `MainChartsSection.vue` (조직별/계획구분별/월별 차트)
  - `DetailTable.vue` (검색/정렬/신호등/진행률 바)
  - `StageMonitoringTabs.vue` (품의/계약/집행 서브탭)
- **상태관리**: 필터 상태(조직/계획구분/품의완료 등)는 Pinia store에서 전역 관리 → API 쿼리 파라미터로 변환
- **반응형**: 원본은 `max-width 1660px` 등 데스크톱 중심 → 반응형 브레이크포인트를 정식으로 설계(태블릿/모바일 대응 여부는 PM 확인 필요)
- **차트 로딩 성능**: 초기 로딩 시 여러 차트를 한번에 그리는 원본 구조 대신, 탭 활성화 시점에 lazy-load

## 3. 백엔드 개발자(BE) 에이전트 — 의견

**역할**: FastAPI 기반 API, 데이터 처리/집계 로직, 데이터 저장소 설계

### 분석
- 원본의 핵심 계산 로직(집행률, 신호등 판정, 월별 누적 집계, 기성 예측 파싱 등)은 순수 pandas 로직이라 **FastAPI 서비스 레이어로 이식 용이**. 단, `.dat`을 매 요청마다 파일에서 읽는 구조는 운영환경에 부적합.
- `기성_월`/`기성_금액`처럼 `/`로 다중값을 넣는 필드는 정규화가 안 된 데이터 모델 → DB로 옮길 때 **1:N 관계(기성 실적 테이블)로 정규화** 필요.
- `담당자(변경전)`, `투자명(변경전)` 필드 존재로 보아 이미 "변경 이력"을 수동으로 남기고 있음 → 이를 **정식 변경 이력(Audit Log) 테이블**로 설계하면 데이터 신뢰성과 감사 용이성이 크게 향상.
- 원본은 `CURRENT_YEAR`/`CURRENT_MONTH_OVERRIDE`로 기준월을 코드에서 고정 — 운영 편의를 위해 API 파라미터/설정값으로 전환 필요.

### 제안 사항
- **기술 스택**: FastAPI + Pydantic v2 + SQLAlchemy 2.0(async) + Alembic(마이그레이션) + PostgreSQL + Redis(캐시) + Celery 또는 APScheduler(월별 집계 배치/알림)
- **데이터 모델(초안)**:
  - `investments` (조직, 담당자, WBS, 투자명, 계획구분, 심의정보, 금액 계열 컬럼)
  - `execution_records` (investment_id FK, 기성단계, 월, 금액, 실적/예측 구분) — 원본의 `/` 다중값을 정규화
  - `investment_history` (변경 이력: 담당자 변경, 투자명 변경, 금액 변경 스냅샷)
  - `data_import_batches` (매월 `.dat`/Excel 업로드 이력, 검증 결과)
  - `users`, `roles` (권한 관리용, 신규)
- **API 설계(초안)**:
  - `GET /api/v1/config` — COL/THEME/KPI_CARDS/필터 정의 등 메타데이터 (프론트 하드코딩 최소화)
  - `GET /api/v1/investments` — 필터/검색/페이지네이션
  - `GET /api/v1/dashboard/kpi`, `/dashboard/charts/{chart_key}` — KPI/차트용 집계 API (원본 계산 로직 이식)
  - `GET /api/v1/status/{stage}` (po|contract|execution) — 상세 모니터링 탭별 데이터
  - `POST /api/v1/imports` — `.dat`/CSV/Excel 업로드 및 파싱·검증(기존 인코딩 자동감지 로직 재사용)
  - `GET /api/v1/investments/{id}/history` — 변경 이력 조회
- **성능**: 집계 API는 Redis에 기준월 단위로 캐시, 데이터 업데이트(신규 import) 시 캐시 무효화
- **검증**: 업로드 시 금액/월 파싱 실패 건을 별도로 리포트(원본의 `clean_money_series`, `extract_month` 관용적 파싱 로직은 유지하되 실패 케이스 로깅 추가)

## 4. Nginx 운영 엔지니어(Infra) 에이전트 — 의견

**역할**: 서빙/리버스프록시, 배포, 보안, 성능 구성

### 분석
- FE(Vue 정적 빌드)와 BE(FastAPI, 보통 Uvicorn/Gunicorn) 두 개의 아티팩트를 Nginx가 통합 서빙해야 함.
- 대시보드 특성상 **엑셀/파일 업로드**(BE 제안의 `/imports` API) 트래픽이 발생하므로 `client_max_body_size` 등 업로드 제한 설정이 필요.
- 차트/테이블이 많아 정적 자산(JS/CSS 번들)이 커질 수 있음 → 캐싱/압축 전략 필요.

### 제안 사항
- **구성**: Nginx가 `/` → Vue 빌드 결과(정적 파일) 서빙, `/api/*` → FastAPI(Uvicorn, 여러 워커를 Gunicorn으로 관리)로 리버스프록시
- **보안**: HTTPS(TLS 종료를 Nginx에서), 사내망이라도 최소 HTTP Basic/사내 SSO 연동 여지 확보, 보안 헤더(`X-Frame-Options`, `X-Content-Type-Options`, CSP) 적용
- **성능**: Gzip/Brotli 압축, 정적 자산 `Cache-Control` 장기 캐시 + 해시 기반 파일명(Vite 빌드 시 기본 지원), API 응답은 캐시 안 함(대시보드 특성상 최신 데이터 중요)
- **업로드**: `client_max_body_size 20m;` 수준으로 설정(월간 `.dat`/Excel 파일 크기 고려), 업로드 타임아웃 조정
- **배포**: Docker Compose로 `nginx / frontend-build / backend / postgres / redis` 컨테이너 구성, 블루-그린 또는 단순 롤링 재시작 전략(팀 내부 시스템 규모 고려 시 과설계 지양)
- **모니터링**: Nginx access/error 로그 → 추후 Loki/Prometheus 연동 여지만 남겨두고 1차는 로그 로테이션(logrotate) 수준으로 충분

## 5. 프로젝트 관리자(PM) 최종 통합 개발 계획

4개 에이전트의 의견을 종합해 다음과 같이 최종 계획을 정리합니다.

### 5.1 최종 아키텍처

```
[사용자 브라우저]
     │  HTTPS
     ▼
┌─────────────────────────────┐
│           Nginx              │
│  /        → Vue 정적 빌드     │
│  /api/*   → FastAPI(Uvicorn) │
└─────────┬─────────┬──────────┘
          │         │
          ▼         ▼
   ┌────────────┐ ┌───────────────┐
   │  FastAPI    │ │  정적 자산 캐시 │
   │  (BE 서비스) │ └───────────────┘
   └─────┬───────┘
         │
   ┌─────┴──────┐
   │ PostgreSQL │──(집계 캐시)──▶ Redis
   └────────────┘
```

### 5.2 데이터 모델 전환 방침
- 1차: 기존 `.dat` 업로드 → 파싱 → PostgreSQL 적재(정규화: investments / execution_records / investment_history)
- 원본의 `COL` 매핑 딕셔너리는 **DB 컬럼 ↔ 표시명 매핑 테이블**로 승격하여 `/api/v1/config`에서 제공 → 컬럼명 변경 시 DB 마이그레이션 없이 표시명만 수정 가능

### 5.3 로드맵 (예시, 6단계)

| 단계 | 기간(예상) | 내용 | 담당 |
|---|---|---|---|
| 0. 요구사항 확정 | 1주 | 범위(조회 전용 vs 입력/승인 포함), 사용자 권한 정책, 알림 필요 여부 확정 | PM |
| 1. 데이터/설계 | 1~2주 | ERD, OpenAPI 스펙, 디자인 토큰/컴포넌트 목록 확정 | PM, BE, FE |
| 2. BE 핵심 개발 | 2~3주 | 데이터 임포트, 대시보드/상세 API, 인증 | BE |
| 3. FE 핵심 개발 | 2~3주 (BE와 병행) | 레이아웃, KPI/차트, 상세 테이블, 필터 | FE |
| 4. 통합/서빙 구성 | 1주 | Docker Compose, Nginx 리버스프록시, HTTPS | Infra |
| 5. 고도화 | 2주 | 알림, 이력 조회, 엑셀 export, 권한별 화면 제어 | 전체 |
| 6. QA/배포 | 1주 | 실데이터 검증, 성능 테스트, 운영 배포 | 전체 |

### 5.4 API 계약 우선 확정 항목 (FE-BE 인터페이스 리스크 최소화)
- `/api/v1/config` 응답 스키마 (KPI 정의, 필터 정의, 컬럼 라벨)
- `/api/v1/dashboard/kpi` 응답 스키마 (6개 KPI 값 + 단위)
- `/api/v1/investments` 페이지네이션/필터 파라미터 규격
- 에러 응답 포맷(공통 에러 스키마)

### 5.5 리스크 및 대응
| 리스크 | 대응 |
|---|---|
| 실데이터가 샘플(34행)보다 훨씬 클 경우 성능 저하 | API 페이지네이션·서버사이드 정렬/검색 필수화, Redis 캐시 |
| `.dat` 파일 포맷이 비정형(구분자/인코딩 혼재) | 원본의 인코딩·구분자 자동감지 로직을 BE 임포트 모듈로 그대로 이식 + 실패 리포트 제공 |
| 팀 내 실제 운영 방식(파일 교체 주체/주기)이 불명확 | Phase 0에서 PM이 반드시 확인 — 조회 전용이면 범위 축소, 입력 워크플로우 필요 시 일정 재산정 |
| 다중값(`/` 구분) 필드의 정규화 실수 | BE에서 파싱 단위테스트 작성, 원본 계산 결과와 마이그레이션 후 결과를 비교 검증(회귀 테스트) |

## 6. Claude가 프롬프트에 없던 부분까지 자체적으로 제안한 아이디어 정리

요청하신 대로, 지시문에 명시되지 않았지만 원본 코드/데이터를 분석하며 **자체적으로 필요하다고 판단해 계획에 반영한 사항**을 정리합니다.

| # | 제안 아이디어 | 왜 필요하다고 판단했는지 | 계획에 반영된 위치 |
|---|---|---|---|
| 1 | **설정(config) API화** — `COL`/`THEME`/`KPI_CARDS` 등을 백엔드가 내려주는 메타데이터로 전환 | 원본이 이미 설정-드리븐 구조였는데, 이를 FE에 하드코딩하면 원본의 장점(컬럼/문구 변경 시 로직 무수정)을 잃게 됨 | 5.1, 5.2, 5.4 (`/api/v1/config`) |
| 2 | **데이터 정규화(1:N 기성 실적 테이블)** | `기성_월`/`기성_금액`이 `/`로 다중값을 담는 비정형 구조라 DB화 시 그대로 두면 집계 로직이 취약해짐 | 3장 BE 분석, 5.2 |
| 3 | **변경 이력(Audit Log) 정식화** | 원본에 `담당자(변경전)`, `투자명(변경전)` 컬럼이 이미 존재 — 팀이 수작업으로 이력을 남기고 있다는 신호로 판단, 이를 정식 이력 테이블로 승격 | 3장 BE 제안, 5.2 |
| 4 | **알림 기능** (심의예정월 경과, 집행 지연 건) | 원본에 "신호등"(🟡) 판정 로직은 있지만 능동적으로 알려주는 기능은 없어, 실제 업무 활용도를 높이려면 필요하다고 판단 | 5.3 로드맵 5단계 |
| 5 | **파일 업로드/검증 워크플로우** | 원본이 "정적 파일을 코드가 직접 읽는" 구조인데, 실서비스에서는 담당자가 주기적으로 데이터를 교체할 것으로 추정되어 업로드 API 및 검증 리포트를 제안 | 3장 BE API 설계, 4장 Nginx `client_max_body_size` |
| 6 | **인증/권한 관리** | 원본에는 로그인/권한 개념이 전혀 없음. 팀 투자 예산 데이터라는 민감도를 고려해 최소 권한 분리(조회자/편집자/관리자)를 신규 요구사항으로 제안 | 3장 BE 데이터 모델(`users`,`roles`), 5.3 5단계 |
| 7 | **캐시 무효화 전략(Redis)** | 조회 전용 대시보드라도 임포트 직후 최신 데이터가 즉시 반영되어야 하므로, 캐시 도입 시 무효화 시점을 명시적으로 설계해야 한다고 판단 | 3장 BE 제안, 4장 Nginx |
| 8 | **엑셀 export 기능** | 원본 상세 테이블이 업무 보고용으로 활용될 가능성이 높아, 다운로드 기능을 고도화 항목으로 제안 | 5.3 로드맵 5단계 |
| 9 | **API 계약 우선 확정(OpenAPI)** | FE/BE를 병행 개발하려면 인터페이스 불일치 리스크가 크므로, 개발 착수 전 스펙 고정 단계를 별도로 명시 | 5.1 로드맵 1단계, 5.4 |
| 10 | **회귀 검증 계획** | 기존 Streamlit 버전의 계산 결과(KPI, 집행률 등)와 신규 시스템의 결과를 비교하는 절차가 없으면 마이그레이션 과정에서 수치 오류가 조용히 발생할 수 있음 | 5.5 리스크 대응 |
